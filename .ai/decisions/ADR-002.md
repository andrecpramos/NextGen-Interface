# ADR-002 — Drift over SQLite for persistence, not Isar

- **Status:** ⚠️ **SUPERSEDED by [ADR-007](ADR-007.md)** — Drizzle, not Drift
- **Date:** 2026-08-29
- **Deciders:** Architect, Backend
- **Supersedes:** —

> **Read ADR-007 instead.** Only the library changed. This document's core argument —
> SQLite over a document store, for relational finance data with recursive category
> roll-ups and real transactions — was never Dart-specific and still governs.

## Context

The finance domain is relational and analytical: transactions join accounts and a
category *tree*; the core queries are aggregations over date ranges and category
roll-ups; budgets compare aggregates against limits. The Query Engine exposes a fixed
set of parameterised queries that the intent engine selects by id.

The blueprint offered Hive, Isar, or Drift/SQLite, with a stated lean toward Drift for
finance. That lean is correct, and this ADR records why definitively.

## Options considered

**Hive** — key-value, no query engine. Aggregations would be written by hand in Dart
over full scans. Disqualified for an analytics-centric domain.

**Isar** — fast, good Dart ergonomics, strong for object graphs and full-text search.
But: no SQL, so aggregations and roll-ups over a category tree are hand-rolled;
relational integrity is by convention; and the encryption/maturity story is weaker for
financial data. Isar's development activity has also been inconsistent, which is a real
risk for a component you cannot cheaply replace later.

**Drift over SQLite** — SQL with compile-time-checked typed queries, real transactions,
foreign keys, recursive CTEs (exactly what a category tree roll-up needs), tested
migration tooling, and SQLCipher for AES-256 at rest. SQLite is the most-deployed
database in existence and will outlive this project.

## Decision

**Drift over SQLite, with SQLCipher for encryption at rest.**

## Consequences

**Positive**

- Aggregations are SQL: `SUM` grouped by category over a date range, with a recursive
  CTE for the category tree. In Isar this is application code, and application code
  that computes money is application code that gets money wrong.
- Real ACID transactions — a transfer touching two accounts is atomic.
- Drift's compile-time query verification catches schema/query drift at build time.
- Tested migration tooling, which matters because migration failure on financial data
  is unrecoverable.
- SQLCipher is a well-understood, auditable encryption path.

**Negative**

- More setup than Isar; codegen step required.
- Raw-write throughput is lower than Isar's. Irrelevant at our data volumes — a heavy
  user generates a few thousand rows a year.
- SQLCipher adds a native dependency and some open cost.

## Binding constraints this creates

1. **The model never emits SQL.** The Query Engine accepts a query id plus typed slots.
   This eliminates the injection class structurally rather than sanitising it.
2. **Money is `int` minor units + currency code.** SQLite has no decimal type, and
   `REAL` for money is a defect waiting to be discovered at reconciliation time.
3. **Migrations are tested from every previously released schema**, with a backup
   taken before migrating and restored on failure.

## Revisit if

Full-text semantic search over memos becomes a primary feature, or the data model turns
out to be genuinely document-shaped in domain #2. Note that SQLite's FTS5 covers most
of the first case without changing engines.
