# ADR-008 — A backend tier exists, but the device stays the source of truth

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Andre, Architect, Security
- **Amends:** [vision.md](../vision.md) principle 4, [sdlc/requirements.md](../sdlc/requirements.md) constraints

## Context

The project structure now separates frontend, backend, and infrastructure. That is a
sound engineering shape, but it sits in direct tension with what the project has said
about itself so far:

> *"Local-first: no server exists in MVP 1–3"* — requirements.md
> *"Core AI functionality should work locally. No mandatory cloud dependency."* — vision.md, principle 4

Having a `services/` and `infrastructure/` tier makes a server *possible*. The risk is
drift: once a backend exists, features quietly start assuming it, and eighteen months
later the offline promise is gone and nobody remembers deciding to drop it.

That failure mode is common and it is worth spending an ADR to prevent.

## Decision

**A backend tier exists in the structure and is optional in the architecture.**

Three rules, in priority order:

### 1. The device is the source of truth

Local SQLite holds the authoritative copy of the user's financial data. The server, if
enabled, holds a *replica*. Conflict resolution favours the device. A user who never
signs in loses no functionality except sync itself.

### 2. Nothing on the critical path may require the network

The core loop — utterance → intent → action → navigation → answer — must complete with
the radio off. This is testable and is already requirement FR-OFF-01. Any capability
that cannot satisfy it is either redesigned or is explicitly marked as an online-only
feature in the registry, visible to the user before they invoke it.

### 3. Inference stays local by default

Cloud inference remains a user-enabled quality toggle, off by default, disclosed at the
time of use, and recorded in the trace ([security.md](../security.md)). A backend tier
does **not** change this. `services/api` must never become the default route for stage 3.

## What the backend is actually for

Deliberately narrow. It exists to serve these and nothing else without a new ADR:

| Purpose | Why it needs a server |
|---|---|
| Multi-device sync | Genuinely impossible locally |
| Account + auth | Only if sync is enabled |
| Encrypted backup / restore | Data durability beyond one device |
| Model manifest hosting | Model distribution ([deployment.md](../deployment.md)) |
| Optional cloud inference | Quality toggle for hard turns |
| Anonymous, opt-in telemetry | Scrubbed per security.md |

## What it is explicitly NOT for

- Holding the primary copy of financial data
- Running the intent router — that belongs on the device, always
- Any capability with irreversible external effects (payments, transfers, sending).
  Out of scope, unchanged, and adding one requires its own ADR plus a security review.

## Implementation shape

```
services/api/          Hono on Supabase Edge Functions — thin, optional
infrastructure/
  supabase/            migrations · RLS policies · seed
  docker/              local stack for development
  ci/                  pipeline definitions
```

Same Drizzle schema targets local SQLite and remote Postgres ([ADR-007](ADR-007.md)),
so sync is a schema-shaped problem rather than a translation problem.

**Row Level Security is mandatory** on every table from the first migration. A
Supabase project without RLS is an open database, and this one would hold financial
records.

## Consequences

**Positive**

- Sync, backup, and multi-device become possible without re-architecting
- Model manifest hosting has a home, which deployment.md needs anyway
- Clean separation makes the offline guarantee *testable*: if `services/` is
  unreachable and the app still passes the MVP scripted set, the guarantee holds

**Negative**

- A server that exists will attract features. Rule 2 is the guard, and it needs
  enforcing in review, not just in this document.
- RLS policies are a new class of security surface with a new class of mistakes
- Two data stores means conflict resolution, which is genuinely hard and is
  deliberately deferred past MVP 1

## Enforcement

- FR-OFF-01 (full MVP scripted set in airplane mode) becomes a **release gate**, not
  just a test. If it fails, the release stops.
- A network-monitor check confirming zero egress with cloud disabled stays in the
  pre-release checklist ([sdlc/testing.md](../sdlc/testing.md)).
- Any PR adding a network call to a core-loop path requires an ADR.

## Sequencing

MVP 1–2 ship with `services/` empty. The structure is there; the server is not built.
This is deliberate: it keeps the offline architecture honest during the period when
the core loop is being designed, which is exactly when shortcuts would be most
tempting.
