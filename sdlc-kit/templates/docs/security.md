### Model output is untrusted input

The failure mode is specific and worth stating: a model produces something that
*looks* like an identifier, a path, a route, or a command, and it is used without
checking that it exists. The mitigation is not "prompt the model better".

| Rule | Enforcement |
|---|---|
| Every model-produced identifier is validated against a registry before use | `{{test/gate}}` |
| The model never emits executable text — no SQL, no shell, no paths | {{architectural test}} |
| Untrusted text is fenced before it enters a prompt | `{{check}}` |
| A user-visible number is computed in code, never generated by the model | code review + {{test}} |
| Unclassified capability fails closed | {{test}} |

**Prompt injection is not solved by instructions.** Text arriving from outside —
a document, a field, a search result — can carry directives. The only reliable
defence is architectural: the model chooses among a fixed set of declared
capabilities, and the dispatcher — not the model — applies the policy for what
each one is allowed to do.

## Review triggers

A security review is required — not optional — when a change:

- crosses or moves a trust boundary
- touches authentication, authorisation, or session handling
- adds a network egress path, or makes an existing one conditional
- changes how secrets are stored, read, or passed
- introduces a dependency that handles untrusted input
