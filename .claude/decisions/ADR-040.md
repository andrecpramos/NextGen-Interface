# ADR-040 — An uncalibrated build does not get a hand-set margin rule; the gap is closed by calibrating sooner

- **Status:** Accepted — 2026-09-25. Proposed the same day, drafted from the
  first production integration's findings at the product owner's request. It **declines** that report's
  recommendation 9 and records why
- **Date:** 2026-09-25
- **Deciders:** Maintainers
- **Relates to:** Rule 14 (thresholds are calibrated, never hand-set or copied);
  [ADR-036](./ADR-036.md) (stage 3 made fast enough to cover the gap).

## Context

On a 130-screen registry with the default thresholds (`tauHigh 0.636`, `delta 0.01`, calibrated on a
7-screen reference app), "who is injured on the team" scored the right screen at 0.59 with the runner-up
at 0.21, and still clarified. Scores on a large registry run lower, while the margin was decisive. The
integration recommended accepting "when top ≥ τ and top − second ≥ δ, with δ scaled for registry size" for
an uncalibrated build.

That is a threshold chosen by hand, with a formula for scaling it that no measurement produced. Rule 14
exists because doing exactly that was measured to fail (more than once). The kit already refuses to
calibrate from the generator's own examples: measured, it made the engine wrongly refuse 7 real requests
in 105, against 1 for the untouched default.

What changed since the report: with ADR-036, a stage-3 turn on qwen3:14b takes ~0.9 s instead of timing
out. An adopter with stage 3 on no longer pays much for the clarify the margin rule would have avoided.

## Decision

1. **No margin- or size-scaled acceptance rule for uncalibrated builds.** Rule 14 stands.
2. **Make calibration arrive sooner.** `doctor` counts the `nextgen:learn` lessons the adopter keeps in
   `lessons.jsonl` in the kit folder: the questions visitors settled by picking a place or saying
   neither. It names `teach` for them and, from 20 on, says there is enough to calibrate. Those are real
   questions, not generator examples. *As built*, it cannot convert them for `calibrate` by itself: a
   lesson carries no role, and the golden file needs one. The developer adds it.
3. ~~**`doctor` says what uncalibrated costs on this registry**~~ **Dropped when built.** Every phrasing
   in the knowledge file is also an example in the registry, so routing them would measure memory (each
   matches its own copy), not what visitors will meet. A number that flatters the default is worse than
   none. Held-out questions are the only honest measure, and item 2 is how they arrive.

## Why not the alternatives

- **Adopt the report's rule.** It is the change Rule 14 forbids, and its δ-for-size scaling is unmeasured.
  The one data point is a single question.
- **Do nothing.** The adopter keeps a timid router until someone writes 20 questions by hand, which the
  first adopter deferred ("later, with 20–30 real questions").
- **Ship per-size default profiles** (small, medium, large registry). This is closer to honest, because
  each profile would be calibrated. But the corpora do not exist: one fixture per size class would have
  to be built and kept.

## The reversibility test

It is a refusal plus a doctor report. It would be cheap to reverse, but it decides a recurring question
against a numbered rule, so it is recorded to stop it being reopened without new evidence.

## Consequences

- **An uncalibrated large registry keeps clarifying on turns it would have got right.** On a build without
  stage 3, the visitor pays that as an extra click, until calibration.
- The lessons that feed calibration hold visitors' own words. Where the adopter keeps them is their privacy
  decision, and until they decide, this path does not start.

## Compliance

Rule 14 remains enforced by `check-thresholds.mjs`. The lessons line is held by `kit.test.ts` ("counts
what visitors settled").
