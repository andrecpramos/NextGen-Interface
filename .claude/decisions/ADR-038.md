# ADR-038 — A turn can be handed to the app's assistant by a rule, before any model is asked

- **Status:** Accepted — 2026-09-25 (chosen to build). Proposed the same day,
  drafted from the first production integration's findings at the product owner's request
- **Date:** 2026-09-25
- **Deciders:** Maintainers
- **Amends:** [ADR-026](./ADR-026.md) — the companion, which today receives only what this assistant
  could not place.
- **Relates to:** [ADR-027](./ADR-027.md) (the `decide` option, whose name this must not reuse);
  Rule 5 (policy is code, not prompt text).

## Context

With the app's own assistant merged in as the companion, users asked the orb for things only that
assistant can do: "cancel tomorrow's session" (prepare a change) and "how many goals did we score" (answer a
fact). The router sent both to a screen. Stage 3's only way out is `out_of_scope`, which means "not about
this app", and its system prompt says "you cannot perform any action", which pulls the model toward screens.

The integration first gave the model an extra id, `__assistant__`, with instructions and examples. Two
wordings of those instructions, on the same 7 captured requests, flipped decisions back and forth: one
handed over "how many goals" but not "cancel", the other the reverse. What held was **deterministic rules on
its stage-3 server, run before any model call**:

- a specific change the assistant can prepare **for this user's roles**, each rule tied to the tool that
  makes the change, so a user who cannot make it is not handed over;
- a question of fact ("how many…", "who scored", "can X play", "what is owed").

A match answers with the out-of-scope id, and the orb passes the utterance to the companion, in 10–15 ms.

Two smaller things came up at the same seam. The orb's panel sat over the companion's panel, and covered
its microphone and send button; this was found only in a real browser. And `nextgen:turn` fires for routed
turns but not for turns the companion answered, so a test harness could see those only by scraping the
shadow DOM.

## Decision

1. **A `handOver` option on the companion**: `handOver?(text, { route }) => boolean`. It runs in the
   browser **before this assistant routes the question at all**. `true` sends it to `companion.ask`, with no
   screen scoring and no model of ours. *As built, this is earlier than the draft's "before stage 3"*:
   Rule 20 (ADR-041) answers a change request with its screen, so a hand-over placed after routing would
   never see "cancel tomorrow's session", which is exactly the request the companion can prepare. It is the
   adopter's code, so it can know the user's roles and the companion's tools. A throw, or the companion
   declining, routes the question as usual. Mashing (ADR-039) is never handed over. `decide` is not reused:
   that name is ADR-027's confirm/balanced/eager.
2. **A handed-over turn is announced as `nextgen:companion`** `{ utterance, handedOverBy: 'rule' |
   'unplaced', latencyMs, answered }`. *As built, it is not a router outcome*: a question the rule claims
   is never routed, so there is no `TurnTrace` for it. Rule 9 covers routed turns, and small talk has none
   either. The event is its record, and `nextgen:turn` is not sent for it.
3. **No companion id is offered to the model by default.** It was measured unstable. It can come later
   behind a flag, once a golden set shows it holds.
4. **The orb steps aside while the companion's own UI is in use.** The handle gets `stepAside()` and
   `comeBack()` (not `yield`, which reads as the keyword). Stepping aside closes the panel and **hides the
   whole widget, orb included**, because the app's panel sits in the same corner. `comeBack()` shows it
   again, reopened if it was open. The companion calls them when it opens a confirmation card, a tour or a
   form.
5. **The reference companion contract says the model never performs a change.** It prepares a proposal,
   the app writes the confirmation sentence and shows it, and the user confirms each step.

## Why not the alternatives

- **Do nothing.** Every adopter with an assistant writes the first integration's server rules again, and
  signals the hand-over by overloading `out_of_scope`. That makes "not about this app" and "for the
  assistant" indistinguishable in every trace.
- **Let the model choose (`__companion__` in the enum).** Measured: two wordings flipped 7 requests in
  opposite directions. A decision that depends on the wording of a prompt is not one to route a change
  request through (Rule 5's reasoning).
- **A built-in verb list per language** ("cancel|move|reschedule …", "how many …"). This is plausible as a
  helper the adopter calls inside `handOver`. As a default it would hand over requests the companion
  cannot serve for this user's role, which is the case the integration's per-role rules exist for.

## The reversibility test

It adds an outcome to the trace's public vocabulary, an event, and two handle methods. Adopters would
depend on all four, so an ADR is owed.

## Consequences

- **The quality of the hand-over is the adopter's code.** A bad rule sends navigation requests to a slower
  assistant, and the orb cannot correct it.
- `handOver` runs on every unsettled turn, in the browser. It must be cheap and synchronous, or it delays
  every turn.
- A claimed question leaves no `nextgen:turn`. A page that logged every turn from that event alone must
  also listen for `nextgen:companion`.
- Because the rule runs before routing, a rule that is too broad takes navigation requests too ("open the
  calendar" claimed by `/calendar/`), and they reach a slower assistant. The adopter's rule is the only
  guard.

## Compliance

`assistant.test.ts` ("the app's own assistant, merged in"): a claimed question never reaches the router
and is announced as `rule`; an unclaimed, throwing or declined one is routed; an unplaced hand-over is
announced as `unplaced`; `stepAside` hides and `comeBack` restores. `declarations.check.ts` holds
`COMPANION_EVENT`, `CompanionTurn`, `handOver`, `stepAside` and `comeBack` in `nextgen.d.ts` to the source.
**Not done:** a real-browser check that nothing is left in the app panel's way. The overlap was found in a
browser and was invisible to unit tests.
