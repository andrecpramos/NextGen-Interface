# ADR-012 — The visual system is a bespoke "graphite HUD", not Material 3

- **Status:** Accepted
- **Date:** 2026-08-30
- **Deciders:** Product, Frontend
- **Supersedes:** the *Visual system* section of
  [ui-guidelines.md](../docs/ui-guidelines.md), which specified Material 3 with dynamic
  colour. Every other section of that document stands unchanged and is implemented.
- **Implements:** WP-08.

## Context

[ui-guidelines.md](../docs/ui-guidelines.md) was written alongside the Flutter proposal,
where Material 3 came free with the framework and dynamic colour was a platform
feature rather than a design choice. [ADR-006](./ADR-006.md) then rejected Flutter for a
TypeScript monorepo, and [ADR-005](./ADR-005.md) fixed the *structure* of the interface —
assistant primary, conventional navigation underneath. Neither revisited the visual
language, so a Flutter-era instruction survived into a stack that gets nothing for
free by following it.

Meanwhile the product direction is explicit: a futuristic, cyberpunk-adjacent surface
that reads as an instrument, built with Apple's design principles, and **without neon
effects**. Material 3 in a browser is a large amount of imported opinion — elevation
tints, state layers, tonal palettes — pointing somewhere else entirely.

## Decision

**A bespoke design-token system, implemented as CSS custom properties in
`packages/ui/src/tokens.css`. No component framework, no utility framework.**

The language, named for what it is:

- **Graphite ground, machined edges.** Deep neutral surfaces; depth from layered
  translucency, hairline borders and a top-edge highlight. Shadows are dark and
  neutral. **No coloured shadow anywhere** — a coloured shadow is a glow, and glow is
  the thing being avoided.
- **Two accents, split by function, not decoration.** Cold desaturated teal for
  AI-originated content — preserving the existing guideline that "the app said this"
  and "the AI said this" are always distinguishable. Warm amber for *waiting on the
  user*. That second accent is load-bearing: it is half of what stops the sphere's
  `confirming` state from reading as `thinking`.
- **Apple's three principles, applied literally.** Clarity (content first, no
  ornament), deference (translucent unlit chrome that sits behind the answer), depth
  (three planes — ground, stage, trace panel — carrying hierarchy so borders need not).
- **System font stack, mono for technical metadata.** Ids, scores, timings and table
  names are rendered in mono; that is the "instrument" texture, and it is also honest
  signposting that those strings are machine records rather than prose.

Full light/dark parity is retained as a hard requirement, and light is a designed
theme rather than an inversion: the accents darken to hold contrast on a bright
ground.

## Rationale

**1. Material 3 buys nothing here.** Its value is a coherent set of defaults and
platform integration. In a hand-built React surface it is a dependency, a bundle cost
and a set of visual decisions that must then be fought — the tonal elevation system in
particular is precisely the "lit surface" look this design rejects.

**2. The interface has one signature component and it is not in any framework.** The
sphere is an eight-state machine rendered as SVG geometry, and the confirmation card
is a form whose whole job is to look checkable. Neither exists in a component library.
The rest of the system is hairlines and type.

**3. Tokens give theming without a build step.** CSS custom properties do light/dark
parity, and a future third theme, with no toolchain and no content-scanning
configuration across a pnpm workspace. That was the alternative considered and
rejected — see below.

**4. "No neon" is a real constraint, not a style note.** The cyberpunk register is
usually carried by saturated glow. Removing it means the register has to be carried by
*form*: machined detail, technical typography, restraint, atmosphere. That is a design
problem, and importing a framework does not solve it.

## Alternatives considered

**Tailwind, as WP-08 originally suggested.** Rejected. In a workspace where the design
system is a separate package consumed as TypeScript source, Tailwind needs content
globs reaching across package boundaries, and every token still ends up defined in a
config file that is one more indirection away from the CSS. The tokens are the design
system; a utility layer over them adds a build dependency and no expressiveness.

**Material 3 via a React implementation.** Rejected on bundle cost and on fighting its
elevation model, per rationale 1.

## Consequences

**Good**

- Zero UI dependencies in `packages/ui`. React is a peer dependency; nothing else.
- The visual language is 200 lines of tokens, so changing it is a diff, not a migration.
- Contrast is verified against the tokens directly, and both themes are checked at the
  point where the colour is defined.

**Bad, or at least a cost**

- Anything a component library would have supplied — a date picker, a menu, a combobox
  — has to be built or brought in when the time comes. Nothing on the current surface
  needs one, and that will not stay true forever.
- Accessible behaviour for future composite widgets is now our responsibility rather
  than a library's. The existing components are simple enough that this is a small
  cost today; it grows with the surface.

**Unchanged**

Every structural rule in [ui-guidelines.md](../docs/ui-guidelines.md) survives this ADR and
is implemented: the sphere as an eight-state machine with `confirming` ≠ `thinking`,
answers rendered rather than narrated, the confirmation card showing parsed parameters
editable in place, the "why?" affordance over a real record, latency-perception
thresholds, the accessibility floor (48px targets, 4.5:1 contrast, 200% text,
`prefers-reduced-motion`, live regions), and 8pt spacing.
