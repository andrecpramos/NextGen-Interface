# ADR-016 — Where the generated registry lives

- **Status:** Accepted, option B, by the owner in session on 2026-09-11. Implementation is scheduled after both open PRs merge (PLAN.md WP-47)
- **Date:** 2026-09-10
- **Deciders:** Architect *(an agent writes this; accepting it is the owner's)*
- **Relates to:** [ADR-011](./ADR-011.md) (generated artefacts in CI),
  [critical-infrastructure.md §1](../docs/critical-infrastructure.md)
- **Owed since:** the collision was first written down. This ADR exists because the
  problem has been described three times and decided zero times.

## Context

`packages/core-intent/eval/registry.json` is **one global path**, and every domain's
`scripts/build-registry.ts` writes it. Only one domain can be authoritative at a time.
Running the other build replaces the registry the router loads with a different
application's capabilities — after which everything downstream keeps working, correctly,
on the wrong application.

The register has carried this since 2026-09-08 with the note *"survivable with two
domains and a documented order; not survivable with three"*. A documented order is a
convention, and this repo's own standard for a convention is that it is obeyed until
someone is in a hurry.

### What has already been done, and why it is not this decision

**2026-09-10:** `checkRegistryOwnership` runs in both build scripts and refuses a write
whose capability namespaces describe a different application. `--force` overrides.

That makes the mistake **loud**. It does not make it **impossible**, and it does not
address the thing that actually constrains the project:

- CI cannot check both domains' generated artefacts in one job, because building the
  second overwrites the first. The staleness gate covers `domain-modules/generated/`
  only — and the last time someone tried to cover finance, the gate diffed a directory
  the build never wrote and passed vacuously for weeks.
- `pnpm router:eval` can only ever measure whichever domain was built last.
- A third domain has nowhere to go.

### The fact that decides this

**The product already requires many registries at once.** Rule 17 says a capability the
user cannot reach is *absent* from the registry they receive, not filtered at render — so
an adopter with ten roles gets ten registries. The generator emits them side by side into
an output directory today.

So the engine is already registry-path-agnostic, and the evidence is that both surfaces
already have the seam:

| Consumer | How it finds the registry |
|---|---|
| `apps/cli` | `options.registryPath`, defaulting to the global path |
| `apps/web` | `findRegistry()` → passes `registryPath` explicitly |
| `core-intent/eval/{evaluate,calibrate,inspect}.js` | **hardcoded** `join(HERE, 'registry.json')` |

**One global path is a leftover from the era when this repo was one application.** It is
not load-bearing for the engine; it is load-bearing for three eval scripts.

## Options

### A. Keep the single path, keep the documented order

Status quo plus the guard. Zero work.

Rejects itself on the third domain, and leaves `router:eval` unable to measure two
applications without a rebuild between runs. It also keeps a shape the product has
already outgrown — the generator's whole output model is many registries at once.

### B. Per-domain output, and every consumer names the one it wants *(recommended)*

Each domain writes `packages/domain-<name>/generated/registry.json`. Nothing writes a
shared path. The three eval scripts take `--registry=<path>`, defaulting to
`domain-modules` so today's commands keep working unchanged.

- Clobber becomes structurally impossible rather than guarded.
- CI can diff every domain's artefacts in one job — the staleness gate stops being
  scoped to whichever domain happened to be authoritative.
- `router:eval --registry=packages/domain-finance/generated/registry.json` becomes a
  real command. Today there is no way to score the router against the second domain at
  all without rebuilding over the first — the engine's domain-agnosticism is asserted by
  construction and never measured end to end.
- Matches the generator: per-role registries side by side in an output directory are the
  same shape as per-domain registries side by side in the tree.

**Cost, honestly:** it moves a committed generated file, so it touches the three eval
scripts, both build scripts, CI's staleness gate, both apps' default paths, and
`.gitignore`/artefact conventions. It is a mechanical change with a wide diff, and a wide
diff to generated-artefact plumbing is exactly where a vacuous gate gets introduced
without anyone noticing — §1 has done this once already.

### C. Per-domain output with no default at all

As B, but every consumer must pass a path; no default anywhere.

Purest, and it makes "which registry?" impossible to get wrong by omission. Rejected as
the recommendation only because it breaks every existing command at once for a
correctness gain B already delivers, and this repo has a working habit of preserving the
command surface across refactors.

## Recommendation

**B**, and the ordering matters more than the choice:

1. Add `--registry=` to the three eval scripts, defaulting to the current global path.
   No behaviour change, no artefact moves. Provable by an unchanged scorecard.
2. Move the write target to `packages/domain-<name>/generated/registry.json` and switch
   the defaults.
3. Widen CI's staleness gate to every domain, in one job.
4. Delete the guard's reason for existing — keep `checkRegistryOwnership`, since a shared
   path could be reintroduced by accident, but its refusal should become unreachable.

Step 1 is independently useful and independently safe. If this ADR is rejected, step 1
still pays for itself.

## Consequences

**If accepted.** One mechanical work package, sequenced above. The staleness gate gets
wider rather than narrower, which is the first time that has been true. `registry.json`
moves, so anything holding the path by hand — including [SETUP.md](../../SETUP.md) and
the two apps' fallbacks — must move with it, and CI must fail if any is missed.

**If rejected.** Record *that* in this file rather than leaving it Proposed. The guard
stays, the documented order stays load-bearing, and the third domain is a known
tripwire rather than a surprise. That is a legitimate choice for a solo project whose
next milestone is a measurement, not a platform — but it should be a choice.

**Either way, the honest note for §1:** the guard shipped on 2026-09-10 changed the
failure from silent to loud and changed nothing else. This ADR is the difference between
a problem that is contained and one that is solved.
