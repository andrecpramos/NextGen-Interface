# ADR-025 — A limit about the assistant acting refuses only a request to act, and a limit points to where the visitor can do it themselves

- **Status:** Accepted — by the owner, in session, 2026-09-25. Proposed 2026-09-22: the owner approved
  building it in session. Extended by [ADR-041](./ADR-041.md): a request to change something is
  offered its screen, never followed there, whether or not a limit is declared
- **Date:** 2026-09-22
- **Deciders:** Andre, Architect
- **Relates to:** [ADR-009](./ADR-009.md) — declared limits refuse by retrieval, not a model's judgement;
  [ADR-015](./ADR-015.md) — the action verb as an independent signal; [ADR-023](./ADR-023.md) — the
  adopter's own limits, from `knowledge.json`; STATUS.md row 10, "declared limits are sticky".

## Context

The generator declares a few limits for every application, from a catalogue of what a navigation
assistant categorically cannot do (`packages/generator/src/boundaries.ts`). Three of them are about the
assistant *doing* something: **acting outside this application** (booking, sending a message), **changing
records for you**, and **processing a payment**. Their examples have to name subjects to be recognisable
— "book a physio appointment for my son", "schedule a doctor's visit for this injury", "send an email to
the coach" — and those subjects are exactly what real screens are about.

Stage 2 judged every limit by topic alone. On the reference app's calibrated profile a limit refuses when
it scores at least level with the best real screen (`boundaryMargin` 0), so a question that shared a
limit's subject was refused whenever the limit edged ahead. Measured on 2026-09-22, with 42 everyday
questions written *before* any change (the reference fixture, `family`, parent and coach roles):

| | |
|---|---|
| Everyday questions wrongly refused | **4 of 42** |
| … of them, refused by one of these three limits | 4 |
| Examples | "injury info for my kid" → *Acting outside this application*; "stop sending me emails" → *Acting outside…*; "change my password" → *Changing records…* |

Refusing a real question is the error this product counts as most expensive: a visitor who is told "I
can't help with that" about something the app does has learned the assistant is not for them.

What distinguishes a request these limits are about from a question on the same subject is the verb —
"book", "send", "change", "pay" — and the engine already reads that, for ADR-015.

## Decision

**We will let a declared limit say that it refuses only a request to act, and have the generator's three
acting limits say so.**

1. The registry contract gains one optional field on `unsupported` capabilities: `refuses: 'action'`
   (`core-capability`). Any other value, or the field on anything but a limit, fails validation.
2. The generator's catalogue sets it on *acting outside this application*, *changing records for you* and
   *processing a payment*. Not on *questions about anything else* (weather, poems — a subject), and not on
   any limit the adopter declares in `knowledge.json`: those are subjects the app does not cover, and are
   still refused on topic.
3. Stage 2 counts a limit marked this way as a candidate only when `isActionRequest(utterance)` — the same
   framing detector ADR-015 uses. Calibration (`scoreTurns`) applies the same rule, so thresholds are swept
   over the router that ships.
4. A registry without the field — every bundle built before this — behaves exactly as before.

**And we will let the assistant help with what it will not do** — the owner's words, 2026-09-22: *"allow
the AI interface to help, not execute, the task we said it wasn't allowed."* A refusal no longer has to
end at "no".

5. A limit may carry `helpAt`: up to two routes where the visitor can do it themselves, or get help with
   it. The adopter writes them in `knowledge.json` (`cannot[].instead`), the installing agent asks for them
   in the interview (ASK 9), and the generator keeps, per role, only the screens that role can open —
   dropping the field when none is left (Rule 17). The validator refuses a `helpAt` route that is not a
   screen of the same registry; a route that is no screen of the app is a `KNOWLEDGE-GAPS.md` entry, never
   silently dropped.
6. The widget answers such a refusal *"I can't do that for you"*, the adopter's own words, and those
   screens as links. For a limit about acting (item 1), with no `helpAt`, it offers the screen the request
   ranks first when that is a plain match — the same "barely a match" bar the likely-one offer already uses
   (0.15), not a new number. A limit about a subject is never given a screen from retrieval alone: measured,
   "quero falar com o treinador" ranks the medical screen first (0.16), which is no help at all.
7. Nothing is performed. The visitor taps, exactly as for any other offer, and "yes" / "the first one"
   work on it as on any offer. `helpAt` is never embedded, so it moves no score.

## Measured

| | before | after |
|---|---|---|
| Reference golden set (69 turns): decisions that changed | — | **0** |
| … right screen executed / out-of-scope refused / in-scope wrongly refused | 34 / 10 of 14 / 0 | 34 / 10 of 14 / 0 |
| Everyday probe (42): wrongly refused | 4 | **2** |
| … "injury info for my kid" | refused | offers the children's and medical screens |
| … "stop sending me emails" | refused | offers notification preferences first |

The two still refused ("change my password", "what's new at the club") carry an action verb or match a
different limit; this decision does not reach them.

## Alternatives considered

- **Do nothing.** Keeps every refusal the golden set has, and keeps refusing everyday questions that share
  a subject with a generic limit. The golden set cannot show the harm: it has no such question, which is
  why this was found only by asking new ones.
- **A floor on a limit's own score, or a larger margin.** A number, chosen after seeing the data — Rule 14
  forbids hand-setting one, and the uncalibrated `boundaryFloor` of 0.15 is already listed as a stand-in
  for that reason. It also cannot separate these cases: "injury info for my kid" and "appointment for this
  injury" score alike, and only the framing differs.
- **Rewrite the catalogue's examples to avoid shared subjects.** Then they stop recognising the requests
  they exist for: "book a physio for my son" *is* about a son and a physio.
- **Drop the generic acting limits.** The action verb alone (ADR-015) would still lower the bar for other
  limits, but nothing would say *what* the app does not do, and the refusal message would be lost.
- **Decide by limit id in the engine** (`unsupported.external_actions`…). No schema change, but the engine
  would know the generator's catalogue by name — the kind of coupling Rule 1's reviewer exists to catch —
  and an adopter could not mark a limit of their own the same way later.

## Consequences

- **A request for something out of scope, said without a verb, is now asked about instead of refused.**
  "Physio appointment for my son" scores 0.45 against *Acting outside this application* and 0.05 against
  the medical screen; it used to be refused, and now the assistant offers the medical screen. The router
  cannot tell it from "injury info for my kid" by topic, and the verb that would tell them apart is absent.
  This is the cheaper error, and the one the product already prefers, but it moves out-of-scope refusal
  down on any set that contains such requests. The reference golden set has none, so its 71.4% is
  unchanged; a real app's number could fall.
- **The contract grows a field**, validated, optional, and read by the engine. Registries are regenerated
  to carry it (`eval/frameworks/family/generated`); a bundle built before this has no field and keeps the
  old behaviour until it is rebuilt.
- **The verb detector now carries more weight.** It is a closed vocabulary in two languages (ADR-015); a
  request to act said with a verb it does not know ("arrange", "tratar de") is not recognised, and an acting
  limit will not refuse it.
- **A wrong `instead` is served as fact.** Like a screen's `purpose`, a route the adopter names is offered
  to visitors as the place to go; if it is the wrong screen, visitors are sent there with the assistant's
  confidence. The interview asks for it rather than guessing it, and only the adopter can get it right.
- **A limit about acting helps less than it could.** Its "do it here" screen comes from retrieval, and only
  above the 0.15 bar; on the reference fixture most acting refusals score no screen that high, so they stay a
  plain refusal. A `helpAt` is the reliable way, and only `knowledge.json` limits can carry one today — the
  generator's catalogue limits cannot know an app's screens.
- **The script tag grows** with this and the rest of the 2026-09-22 understanding work: 51.2 KB → 54.9 KB
  gzipped, most of it the word bridge's list and the follow-up phrases.
- Measured on author-written questions, one fixture, 42 + 69 turns. The owner's acceptance run is the first
  measurement on real ones.

## Compliance

- **Enforced:** `acting-limit.test.ts` (unmarked refuses on topic; marked asks; a request to act and a
  topic limit still refuse); `registry.test.ts` (`refuses-known`, `refuses-misplaced`); the generated-golden
  gate (`evaluate-golden.mjs --check`), which fails if any golden decision moves; `check-derived-artefacts`,
  which fails if the committed registries were not regenerated. For `helpAt`: `registry.test.ts`
  (`help-at-reachable`, `help-at-misplaced`), `emit.test.ts` (kept per role, dropped when none is left, and
  every role's registry still validates), `knowledge.test.ts` (`instead` parsed, a non-route dropped with a
  reason, an unknown route a gap), `present.test.ts` (offered beneath the refusal; nothing for a subject
  limit from retrieval; never another limit or the current page).
- **By convention only:** that no adopter-declared limit is marked `refuses: 'action'` when it is really a
  subject. Nothing stops an adopter hand-editing a registry; `knowledge.json` has no way to say it.
