# ADR-010 — Money: signed integer minor units, currency-bound, sign owned by the domain

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Architect, Backend
- **Extends:** [ADR-007](./ADR-007.md), which chose integer minor units but did not say
  what the integer *means*.

## Context

WP-02's unit tests found three things `resolveMoney` does silently, none of which anyone
had decided:

| Input | Result | |
|---|---|---|
| `"-50"` | `+5000` | leading minus dropped |
| `"minus 50 euros"` | `+5000` | `"minus"` is not a number word |
| `"convert 50 euros to dollars"` | `EUR` | first currency wins by declaration order |
| `"12.345"` | `1234` | truncated, not rounded |

They survived because no golden-set entry exercises them. They are pinned by
`DECISION OWED` tests and were deliberately left unfixed in `core-intent`: what a
negative amount *means* is a property of the finance domain, and a domain-agnostic
router has no business inventing it.

WP-04 defines the money column, so it has to be decided now.

## Decision

**1 · `amountMinor` is a signed integer in the currency's minor unit.**

Negative is money leaving the account, positive is money arriving. A refund is a
positive amount in an expense category; a salary is a positive amount in `income`.

The alternative — an unsigned magnitude plus a direction column — was rejected. It makes
every aggregate a `CASE` expression, and the one thing that must never be wrong is a
sum. With signed amounts, "what is my balance" is `SUM(amountMinor)` and cannot
disagree with itself.

**2 · The sign is applied by the domain, never by the parser.**

`resolveMoney` keeps returning an unsigned magnitude. It is a *speech* parser: "twenty
euros" and "minus twenty euros" both mean the quantity 20, and which direction that
moves is decided by the capability that received it — `transaction.create` in an expense
category is an outflow, in `income` an inflow.

So the WP-02 behaviour is **correct as it stands**, for a reason that had not been
articulated. What was wrong was that it was silent about it. The tests now say so.

The one genuinely unhandled case is an explicit "refund of 20" recorded against an
expense category. That needs a capability that declares its direction, not a smarter
parser. Tracked for WP-07.

**3 · Currency is bound to the account, and a mismatch is refused — never converted.**

Every `amountMinor` carries a `currency`, and it must equal the currency of the account
it belongs to. A transaction that disagrees with its account is rejected at the
repository boundary.

There is no conversion anywhere in this system. Converting requires a rate, a rate has a
date and a source, and a wrong rate silently corrupts every historical aggregate. When
an utterance names two currencies the parser will keep picking the first; the *domain*
must reject it and ask, rather than guessing which one the user meant.

**4 · Aggregates are currency-aware or they do not run.**

Any query summing across accounts either filters to one currency or groups by it.
`SUM(amountMinor)` over mixed currencies is not a number, and the design note in
[sdlc/design.md](../sdlc/design.md) already said so: "currency travels with the amount —
a multi-currency account set makes aggregation currency-aware or wrong."

**5 · Parsing rounds half-up at the minor unit; storage never sees a float.**

`"12.345"` truncating to `1234` was an artefact of the capture regex, not a decision.
Sub-cent input is not meaningful here, but "truncate" and "round" are different answers
and the code should state which. Rounding half-up is the one users expect.

No `real`/`float`/`numeric` column ever holds money. `Number.isInteger` is asserted on
the way in.

## Consequences

**Positive**

- `SUM(amountMinor)` is always correct and always cheap.
- Refunds, corrections and transfers between own accounts are all representable without
  a special case.
- The parser stays domain-free, so a second domain reusing `core-intent` inherits no
  finance opinions about signs.
- Refusing conversion removes an entire class of silent historical corruption.

**Negative**

- "Spending" is `SUM` of the *negative* amounts, which reads slightly awkwardly in every
  query and is easy to get wrong once. It is written once, in the query engine, and
  tested.
- Users who name two currencies get a clarifying question rather than an answer. That is
  the intended behaviour and it will occasionally feel pedantic.
- A cross-currency account set cannot show a single net-worth figure. Correct, and worth
  the friction.

## Enforcement

- `amountMinor` is `integer` in both dialects; a `real` money column fails review and
  the schema-parity test.
- The repository rejects a transaction whose currency differs from its account's.
- The query engine's aggregate queries take a currency and filter by it; there is no
  overload that omits it.
- `assertMinorUnits()` throws on a non-integer, and is called on every write path.
