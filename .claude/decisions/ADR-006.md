# ADR-006 — TypeScript monorepo, superseding Flutter

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Andre, Architect
- **Supersedes:** [ADR-001](./ADR-001.md)

## Context

ADR-001 chose Flutter + Riverpod + GoRouter. It was written to the project
blueprint's stated preference, before any evidence about the developer's actual
working stack existed. That evidence has since been gathered.

Across the developer's existing repositories:

| Repo | Stack |
|---|---|
| `judo_app` | Next.js, React, TypeScript, Tailwind, Supabase, Vitest |
| `Branches_CV` | Next.js, React, TypeScript, Tailwind, Zustand |
| `WeFitAll` | React, Vite, Vitest, Supabase |

No Dart. No Flutter. Flutter is not installed on the development machine.

Two further facts weigh on this:

1. This is a **solo project** with an ambitious scope — an intent engine, an
   inference runtime, a voice pipeline, and a finance domain. The AI-native parts
   are the hard, novel work. Spending the first months also learning a new
   language and framework loads risk onto the wrong thing.
2. The Sprint 0 router spike — a calibrated three-stage cascade, a 200-entry golden
   set, and eight scorecards — is **already TypeScript-compatible JavaScript**. Under
   ADR-001 it would be rewritten in Dart. Under this ADR it becomes
   `packages/core-intent` unchanged.

## Decision

**TypeScript everywhere, in a pnpm workspace monorepo.**

| Layer | Choice |
|---|---|
| Web | Next.js (App Router) + Tailwind |
| Mobile | Expo / React Native |
| Desktop | deferred — Electron or Tauri, decided when it matters |
| State | Zustand (matches `Branches_CV`) |
| Local DB | SQLite — `op-sqlite` on mobile, `better-sqlite3` on desktop |
| ORM | Drizzle ([ADR-007](./ADR-007.md)) |
| Backend | Supabase, optional and off the critical path ([ADR-008](./ADR-008.md)) |
| Inference | Ollama (desktop) · `llama.rn` (mobile) · WebGPU (web) |
| Testing | Vitest |

## Consequences

**Positive**

- The stack matches existing expertise exactly. Effort goes into the novel parts.
- The spike survives as a package. The golden set, thresholds, and scorecards keep
  their value instead of being reproduced in another language.
- One language across web, mobile, backend, and tooling means the intent engine is
  literally the same code on every target — which is the strongest possible version
  of the "domain-agnostic core" claim in [architecture.md](../docs/architecture.md).
- Supabase is already familiar from two other repos.

**Negative — and this is a real cost, not a formality**

- **On-device inference is weaker than Flutter's.** `dart:ffi` → llama.cpp is mature,
  clean, and well-trodden. `llama.rn` works and is actively maintained, but it is a
  smaller ecosystem with fewer people hitting the same problems. This is the single
  thing ADR-001 was genuinely better at, and we are choosing to give it up.
- React Native requires more per-platform native handling than Flutter for FFI-shaped
  work.
- Desktop is no longer nearly free. Flutter gave Windows/macOS/Linux for very little;
  here it is a deliberate additional target.

**Neutral**

- Web still cannot run llama.cpp — but that was equally true under ADR-001. WebGPU
  runtimes (`wllama`, `web-llm`) are, if anything, a better web story than Flutter web.

## Risk this creates, and the mitigation

The mobile inference risk is real and is now the project's largest technical unknown,
alongside the untested 1B model question.

Mitigation: `packages/core-inference` defines one interface with swappable
implementations. The cascade in `core-intent` does not know which runtime it is
talking to. If `llama.rn` proves inadequate, the replacement is one package, not a
rewrite — and stages 1 and 2 keep working regardless, because they never call a model.

## Validation gate

Before MVP 1 commits to mobile: build a throwaway Expo app that loads a quantised
1–1.5B GGUF via `llama.rn` and completes ten stage-3 calls on a physical mid-range
Android device. Measure first-token latency, peak memory, and thermal behaviour.

If that fails, the options are a cloud-assisted mobile path or a desktop/web-first
MVP — decided then, with data, not now.

## What carries over from ADR-001 unchanged

The *architecture* was never Flutter-specific and does not change:

- The capability registry remains the single generated source of truth
- Navigation decisions remain validated against the registry before execution
- The dependency rule (`core` never imports domain) is now enforced by workspace
  package boundaries, which is **stronger** than the lint rule ADR-001 relied on —
  an unlisted dependency simply will not resolve
