# ADR-020 — The generator reads an application's rules, and everything it infers carries where it came from

- **Status:** Accepted — by the owner, in session, 2026-09-18
- **Date:** 2026-09-18
- **Deciders:** Andre, Architect
- **Relates to:** [ADR-019](./ADR-019.md) — prose is what makes this knowledge reach a
  visitor; [ADR-009](./ADR-009.md) — declared limits; Rules 13, 15 and 16.

## Context

The owner's requirement, 2026-09-18:

> *"A nossa integração precisa do máximo de knowledge do nosso adopter's codebase, isto
> irá incluir lógicas, business rules, arquitetura, design systems, navigation etc."*

**Design systems are already done** and are not part of this decision:
`packages/embed/src/theme.ts` reads the adopter's computed styles at run time — background,
typeface, brand colour, corner radius — and enforces 4.5:1 contrast rather than assuming it.

What the generator reads today is the **shape** of an application: its route table, its
role guards, its page markup and headings, its i18n files, and the fields of the forms it
renders. What it does not read is anything about **how the application behaves**: what a
field must contain, what makes an action available, what a screen requires before it will
accept anything.

Without that, the assistant can take someone to the expense form. It cannot tell them the
receipt is required, or that a claim over a threshold needs a manager, because nothing in
the registry knows.

**The owner was offered three depths and chose the deepest:** declarative sources *and*
imperative logic — conditions in handlers and effects — over declarative-only, and over
having the adopter write the rules by hand.

**What that choice costs, measured here, not hypothesised.** WP-42 audited generated
descriptions and found the one clear failure had a single cause: the generator described a
screen from the only literal text under it, which happened to be an error boundary's
fallback. *"A user tries to view comments but sees an error message."* The page shows a
discussion. Nothing was wrong with the model or the prompt — the extractor handed over the
wrong source. Reading imperative code multiplies the number of places that can happen.

## Decision

**The generator extracts application rules, and no inferred rule ships without provenance
and a confidence tier. What it is not sure about goes to `review/`, never to a visitor.**

### Two tiers, and they are treated differently

| Tier | Where it comes from | Where it goes |
|---|---|---|
| **Read** | Validation schemas (zod, yup, react-hook-form resolvers), `required`/`min`/`max`/`pattern` on real controls, TypeScript enums and unions, route guards, navigation hierarchy | the shipped registry |
| **Inferred** | Conditions in handlers and effects — an early `return`, a disabled submit, a thrown error with a message | the shipped registry **only** when the pattern is one the extractor recognises exactly; otherwise `review/INFERRED.md` and nothing else |

### Every rule carries its source

`explanationSource` already exists on a capability for exactly this reason. It is extended:
every extracted rule records the **file and line** it came from, and its tier. Three things
follow, and each is worth the field on its own:

1. A developer reading `doctor` can check any rule against the code in one jump.
2. A rule whose source no longer exists is detectable — an extracted rule can go stale
   exactly like an index, and this makes it gateable.
3. When the assistant states a rule to a visitor, the trace names where it came from. That
   is Rule 9 holding for a new kind of claim.

### An inferred rule is phrased as an observation, not a law

A rule from a validation schema is what the application enforces and may be stated:
*"Amount is required."* A rule inferred from a handler's condition is what the code
appeared to do, and is stated as such: *"The form asks for a receipt before it will
submit."* The distinction is carried in the data, not left to the model's tone
([ADR-019](./ADR-019.md)'s validator sees the tier).

### Rule 16 is untouched, and narrowed rather than widened

This reads more of the adopter's code and still writes nothing into it. The fingerprint
check in `check-adapter.mjs` covers the whole source tree before and after a run, and it
covers this too.

**The edits an adopter's agent may make are now enumerated** rather than left to judgement,
because "seamless" must not become "helpful with someone else's repository":

1. the one script line, in the page — `AGENTS.md` ASK 3;
2. a handler that serves `bundle/` per role — ASK 1;
3. a `nextgen:navigate` listener, in their own router code — ASK 5;
4. a `.gitignore` entry — ASK 4;
5. a stage-3 endpoint, if they enable it ([ADR-017](./ADR-017.md)).

Nothing else, and each with the developer's answer first. An agent that finds itself
editing anything else has misunderstood, and `AGENTS.md` says so.

## Why not the alternatives

**Declarative sources only.** Recommended, and rejected by the owner. It is the tier where
every rule is read rather than guessed, and it would have covered required fields, enums
and guards — most of what a form needs. It cannot see *"submit is disabled until the
manager has approved"*, which lives in a condition.

**Have the adopter declare the rules by hand.** The only path where nobody ever asserts
something the application does not do. Rejected as too slow to adopt: a tool whose value
appears after a day of writing declarations will not be tried.

**Extract everything and let the model sort it out.** This is the version this decision
exists to prevent. WP-42's finding is that extraction quality, not model quality, decides
description quality; handing a model more unfiltered source makes it fluent about the
wrong things.

## The reversibility test

**Cheap to narrow, expensive to widen after shipping.** Demoting the inferred tier to
`review/`-only is one flag and returns the product to the declarative-only option. But a
rule a visitor has relied on is a rule that cannot be quietly removed, which is why the
tier is in the data from the first version rather than added when it starts hurting.

## Consequences

- **Rule 13 gains a sibling.** Limits are declared, never judged by the model; rules are
  now *extracted*, never judged by the model either. The model phrases them; it does not
  decide them.
- **`review/` becomes something a developer must read**, not only something they must not
  serve. `doctor` says so.
- **A new staleness surface.** An extracted rule points at a line; the line moves. The
  derived-artefacts gate grows a check that every recorded source still resolves.
- **More untrusted text reaches prompts** (Rule 15). Fencing is unchanged; the volume grows
  and `check-prompt-fencing.mjs` still covers the sites.
- **The honest risk, stated:** an inferred rule can be wrong, and a wrong rule stated
  confidently is worse than no rule. Provenance makes it findable and the tier makes it
  hedged; neither makes it true. The golden set gets a bucket for rules, and the first
  adopter's run is where this is really tested.
