# ADR-037 — Voice may be recognised by the app's own server, never by a third party's

- **Status:** Accepted — by the owner, in session, 2026-09-25 (chosen to build). Proposed the same day,
  drafted from the first production integration's findings at the owner's request. Rewords Rule 8
- **Date:** 2026-09-25
- **Deciders:** Andre, Architect
- **Relates to:** Rule 8 and [ADR-017](./ADR-017.md) (escalation only to the adopter's own origin);
  `packages/embed/src/voice.ts`.

## Context

`voice.ts` uses speech-to-text only through a recogniser that reports `processLocally` and says it is
`available()` on the device. The intent is sound: Chrome's default recogniser streams audio to Google, and
Edge's to Microsoft.

The first production integration (pt-PT, 10 roles) found that this makes voice unavailable almost everywhere
for a language other than English. Brave exposes the API with nothing behind it (every attempt fails with
`network`). Firefox has no API. iOS is unreliable. Chrome and Edge have an on-device pt-PT model only when a
language pack is installed.

The integration's fix was a server-backed recogniser, passed through the `voiceEnv` option, which is a test
seam and not in `nextgen.d.ts`. It records with `MediaRecorder`, detects the end of speech, uploads to the
app's own speech-to-text endpoint (self-hosted Whisper), and returns one final result. It declares
`processLocally` honestly, in the sense the check intends: the audio goes to the app's own server, never to
a speech vendor. It worked in every browser tried, including iPhone, Android, Firefox and Brave. The
integration pins `voiceEnv` with a test that reads the runtime file, because an upgrade that dropped it
would mute voice without an error.

The speech detector it needed is a finding in its own right. On a real webcam microphone with noise
suppression on, the room measured RMS ≈ 0.0016 and speech from a metre away stayed under 0.012. A fixed
threshold of 0.012 never fired, so nothing was uploaded, and the server logs showed zero requests. The
first samples are exact zeros while the suppressor settles, so a "room = minimum of the first 300 ms" rule
measured silence. What worked: the room level is the median of the non-zero samples in the first 300 ms,
capped at ≈ 0.006; it follows the room slowly (`room = 0.98·room + 0.02·rms` while below the threshold);
speech is RMS ≥ max(0.004, 3 × room); a take ends after 1.0 s of quiet. The runtime's own
`voiceActivity()` uses fixed `start = 0.12`, `stop = 0.05`.

## Decision

1. **The privacy rule becomes "never a third party's speech service".** Audio may go to the adopter's own
   origin, on the same terms as a stage-3 turn (Rule 8, ADR-017): off by default, and only to a path
   resolved same-origin, checked the way `SameOriginLlmRuntime` checks its path.
2. **A public `transcribe` option**, `{ path: string, fetch?: (url, init) => Promise<Response> }`. With it,
   the widget records one utterance, POSTs it to the path, and reads back `{ text }`. Without it, only
   on-device recognition is used, as today. `voiceEnv` stays a test seam.
3. **The endpoint contract is OpenAI-compatible** (`/v1/audio/transcriptions`, multipart `file`,
   `language`, `response_format=json`), so speaches, faster-whisper servers and hosted APIs work behind the
   adopter's own proxy. `adapter/AGENTS.md` gets a reference proxy, with the settings the integration
   measured: `large-v3-turbo` int8 on 8 CPU threads ~3.5 s, `small` int8 ~1.2 s; kept loaded and warmed at
   start; `vad_filter`, `temperature 0`; a vocabulary prompt of ≤ ~600 characters; and segments with
   `no_speech_prob > 0.6 && avg_logprob < −1` dropped.
4. **The speech detector adapts to the room**, as measured above, and replaces the fixed levels. A tapped
   take that heard sound but no clear speech is uploaded anyway, and the server's voice-activity filter
   decides. Hands-free listening never uploads without speech.
5. **Every failure says why:** permission refused, no microphone, not a secure context (plain http on a LAN
   address), nothing heard, service down, rate-limited. There is a visible phase ("listening…",
   "transcribing…") and a live level ring.

## Why not the alternatives

- **Do nothing.** Voice stays on-device only. For most visitors outside English it never appears, and each
  adopter who wants it rebuilds the first integration's recogniser on an undocumented seam.
- **Allow the browser's cloud recogniser.** That sends visitors' audio to Google or Microsoft with no
  agreement between them and the adopter, which is exactly what the rule exists to prevent.
- **Document `voiceEnv` as public.** It exposes the whole browser surface (`AudioContext`, timers,
  `getUserMedia`) as API. `transcribe` is one path and one optional fetch, and the widget keeps the
  recording and detection that every adopter would otherwise get wrong.

## The reversibility test

It crosses layers (widget, adopter guide, a new adopter endpoint) and changes what Rule 8 allows. An ADR is
owed.

## Consequences

- **Audio leaves the visitor's device.** It goes only to the adopter's own origin, but to a server, and the
  adopter becomes responsible for storing none of it. The adopter guide must say so, and doctor must print
  it when `transcribe` is set.
- **An endpoint that runs a model on uploaded audio is expensive to call.** It needs the same
  authentication and rate limits as stage 3.
- The adaptive detector is tuned on one microphone and one synthetic voice through a fake device. Real
  accented voices on phone microphones were **not** tested.
- Whisper pads every request to a 30-second window, so a 3-second question costs about as much as a
  30-second one. The CPU latency floor is the encoder, not the audio length.

## As built (2026-09-25)

- `transcribe: { path, fetch? }` (`AssistantOptions`, `StartOptions`, `nextgen.d.ts`) and
  `data-nextgen-transcribe="/api/transcribe"` on the script tag. `server-voice.ts` is a recogniser with the
  browser's own shape, so `converse()` drives it unchanged: one utterance per `start()`, recorded as Opus at
  32 kbps (`audio/mp4` where WebM is not supported), POSTed as a form (`file`, `language`,
  `response_format=json`), and `{ text }` read back as one final result.
- **Never uploads without speech**, tapped or hands-free. The draft's "a tapped take that heard sound
  uploads anyway" was left out: the recogniser cannot tell a tap from hands-free listening, and uploading
  the room is the failure that matters more.
- The room-adaptive detector (`speechDetector`) decides when a take ends. The widget's own level meter
  (`voiceActivity`, fixed levels) still drives only the orb's animation, never recognition, so it was left
  alone.
- Failures are said: "not allowed", "no microphone could be opened", "voice is not working right now".
  There is a new "Writing down what you said…" phase. The level ring was already there.
- **Not built:** a microphone picker; a message for a non-secure context (on plain http the microphone is
  simply not offered); a `doctor` line, because `transcribe` is a start option `doctor` never sees. The
  adopter guide says it instead.

## Compliance

`server-voice.test.ts`: another site's path is refused with no request; the recogniser passes
`processLocally`; one utterance is sent to this site with its language and returns one final result;
nothing is sent when nothing was said; the app's authenticated client is used and a 401 is reported as
`service-not-allowed`. The detector is tested on the measured webcam levels, the settling zeros, the cap
and the give-up. `check-network-egress.mjs` still holds: the path is resolved against the page, never
written into the widget. **Not measured:** real voices on phone microphones.
