# ADR-011 — CI gates on deterministic runs and tolerances, never on model accuracy

- **Status:** Accepted
- **Date:** 2026-08-30
- **Deciders:** DevOps, QA
- **Implements:** WP-12. **Depends on:** [ADR-003](./ADR-003.md) (three-stage cascade),
  [ADR-006](./ADR-006.md) (TypeScript monorepo — the pipeline in
  .claude/docs/deployment.md still described Flutter jobs).

## Context

WP-12 asks for a pipeline that gates the golden set. The obvious implementation —
run the evaluator, require it to pass, diff the scorecard — fails for three
independently sufficient reasons, each measured rather than assumed.

**1 · The model-backed cascade is not reproducible.** WP-01 Finding 10: two runs of
`llama3.1:8b` at temperature 0, identical input, flipped **7 of 200** golden-set
entries. Gating on exact scorecard equality would fail builds that changed nothing.

**2 · The buckets are too small to measure the targets.** Four of seven golden-set
buckets hold 20 entries. A 20-entry bucket cannot resolve a 95% target to better
than ±5% — one entry *is* five points. Tightening the comparison below the
measurement resolution manufactures noise, it does not find defects.

**3 · A hosted runner cannot run the model at all.** Stage 3 needs Ollama serving
`qwen2.5:1.5b`; a GitHub-hosted runner has neither the weights nor the VRAM.

There is also a failure mode a diff cannot catch. During WP-01 a committed
scorecard was found asserting a `tauFloor` the codebase had already abandoned. It
was committed, internally consistent, and **wrong** — it described a configuration
that no longer existed. It went stale within hours of being written. Nothing in a
per-entry diff would ever have surfaced that, because the file did not change; the
code underneath it did.

## Decision

**1 · CI gates only on the deterministic floor.** `--embedder=hashing --no-stage3`
is the sole cascade configuration CI runs. Per PLAN.md §10 it is the only
deterministic run, which is precisely what makes it the regression net. Verified
here: two consecutive floor runs produced byte-identical accuracy on all five
gates.

**2 · Accuracy is compared to a committed baseline within ±0.05, not to absolute
targets.** The floor run *fails* its own absolute gates by design — top-1 is 0.408
against a 0.90 target, because stage 3 is switched off. The question CI asks is not
"is the router good?" but "**did this change make it worse?**"

**3 · Latency is never compared.** The same two identical runs moved p95 from
0.228 ms to 0.277 ms — a 21% swing carrying no information about correctness. A
latency gate on a shared runner measures the runner.

**4 · Safety violations get no tolerance.** Zero is the only passing value. A
destructive capability executing without confirmation is not a statistical
fluctuation.

**5 · Threshold staleness is its own gate.** A committed scorecard whose
`config.thresholds` differ from `thresholdsFor(embedder)` in `config.ts` fails the
build. This enforces Rule 14 — thresholds are calibrated per encoder, never
hand-set — by making a scorecard that has drifted from its configuration
unmergeable.

**6 · Model-backed evaluation stays a human-invoked step.** `pnpm router:eval` and
`router:calibrate` are run locally against a warm Ollama, and their scorecards are
committed. If they are ever automated, it is on a self-hosted nightly, never
per-PR, and the ±0.05 tolerance still applies.

## Consequences

**Good.** The pipeline is reproducible, needs no GPU, no model download and no
self-hosted runner, and finishes in minutes. It catches the regressions that
matter — a broken retrieval change moves the floor immediately, because stages 1
and 2 are exactly what the floor exercises. It also catches a whole class of
documentation rot that no diff-based check can.

**Bad.** Stage-3 regressions are invisible to CI. A change that breaks only the
model-backed path — a prompt edit, a `topK` change, a parser fix — passes green
and must be caught by a human running `pnpm router:eval` before merge. This is a
real gap and is accepted knowingly: the alternative is a flaky gate, and a gate
people learn to ignore is worse than an absent one they know to compensate for.

**Also bad.** A genuine improvement larger than the tolerance requires committing a
new baseline, so the scorecard becomes a file that must be maintained. The gate
reports improvements explicitly to make that obvious rather than silent.

## Alternatives rejected

**Exact scorecard equality.** Flaps on documented non-determinism. Rejected by
Finding 10 before it was ever written.

**Absolute gates in CI.** The floor cannot pass them, and the configuration that
can does not run on a hosted runner.

**Self-hosted runner with Ollama, per-PR.** Real infrastructure and ongoing cost
for a solo-developer repo, and it does not fix non-determinism — it relocates it.
Reconsider when there is more than one committer.

**No golden-set gate, review only.** This is what produced the stale scorecard.
