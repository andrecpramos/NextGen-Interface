# ADR-031 — It uses the app as a user would: it opens what the visitor asked to start, and presses only what can only open

- **Status:** Proposed — the owner asked for it in session, 2026-09-23 ("the interface helps me locate
  the exact widget that the user has to interact [with] … 'I want to schedule an event' … navigate to
  [the] correct page and open the form for the event. Doesn't fill in (yet at least) … lets make sure our
  work is not 100% specific to Pilot-A"); this text awaits acceptance
- **Date:** 2026-09-23
- **Deciders:** Andre, Architect
- **Relates to:** [ADR-025](./ADR-025.md) (the assistant helps, it does not act), [ADR-026](./ADR-026.md),
  [ADR-029](./ADR-029.md) (a guest on the page; `safeRoute`), WP-27 (guided steps, `anchor.ts`: *"a
  confidently wrong hint is worse than none"*), Rule 15 (adopter text is untrusted).

## Context

Until now the assistant ended at a page. *"I want to schedule an event"* led to the calendar, and the
visitor was left to find "New event" on it. That is the step a newcomer is worst at. They do not know the
app's words for things or where its controls live.

Three things constrain how it is closed:

1. **It must work on any app.** Reading "the button that opens the event form" from source means one
   parser per framework and per UI library. The generator reads React, Vue, Angular, Svelte and plain
   HTML routes, but a control's *handler* can only be read reliably in TSX. A page rendered on the server,
   a micro-frontend, or a framework we do not know would get nothing.
2. **Pressing is an act on someone else's app.** "New invoice" in one app opens a form. In another it
   creates a draft invoice on the server the moment it is pressed. The label cannot tell them apart. The
   product's promise, in its own words to visitors, is *"I don't change anything"*.
3. **A wrong press is worse than none** (WP-27's principle for anchors). Pressing the wrong one of two
   similar controls opens the wrong thing, confidently.

## Decision

We will have the widget, on the page a question led to, find the control that starts what was asked by
**reading the rendered page as a user does**, and press it **only when there is evidence it only opens
something**; otherwise it points at it, and some controls it never touches.

**Finding it (`act.ts`, runtime, any app).** Candidates are the page's buttons, links, tabs, menu items
and `<summary>`s, each named by its accessible name (`aria-label`, else its text, else `title`). It
excludes our own host, anything hidden, inert or disabled, anything inside a `form`, submit and reset
buttons, and the app's navigation (the router already chose the page). The question is reduced to a
**task**: its content words in English and Portuguese, plus the destination's name, and whether it asks
to *start* something (a closed list of verbs: schedule, add, create, new, book, request, marcar, agendar,
criar, adicionar, novo…). A control starts the task when its name has a start verb (or a leading `+`, or
it is declared) and the rest of its name matches the task's words, accents, case and plurals aside, with
near-cognates ("event"/"evento") meeting. A tab matches when every word of its name is in the task.

**What it may press.** Only a control with evidence that it opens rather than does:
- a link to a path on this site (`safeRoute`);
- a tab;
- `aria-haspopup`, `aria-expanded`, `aria-controls`, or a `<summary>`;
- a name the registry lists in the screen's `opens`. The generator writes it from the page's source:
  - React/TSX: a `…Trigger` other than an `AlertDialog`'s, or an `onClick` that only sets state that shows
    something (`setOpen(true)`, a toggle, `openX()`);
  - Vue, Svelte, Angular and HTML templates: a click handler that only sets a flag true, toggles it, or
    calls `open…()`/`show…()`/`toggle…()` (`@click="open = true"`, `on:click={() => (open = true)}`,
    `(click)="openDialog()"`).

  The adopter can also write it in `knowledge.json` (`screens[route].opens`), for any framework.

**What it matches against.** The visitor's words count in full. The destination's name counts half, in
every language the app ships (its title and each translation, ADR-030); that is how "I want to create
one" on Announcements finds "Novo anúncio". The adopter's glossary adds the app's term for what people
say ("o meu filho" → "educando").

**Finding the screen for a task.** A control that starts something names the task in the app's own words,
so each opener's label becomes a matching example for its screen. So does the thing it starts, paired
with the usual verbs in the label's language ("Novo anúncio" gives "novo anúncio", "criar anúncio",
"adicionar anúncio"; at most six per screen).

**What it only points at.** Any other matching control gets the guide's ring and card: *"Tap «New invoice»
to start."*. The press is the visitor's.

**What it never touches.** A control whose name saves, sends, pays, deletes, cancels, confirms, approves,
publishes, archives, closes or signs out (a closed EN/PT list, and "log out"/"sign out" as phrases). It
never types. It never touches anything inside a form, so it never submits.

**Ambiguous is nothing.** Two different controls scoring equally means no action. The same name twice (a
header button and an empty state's) is one. A bare "New" or "+" counts only when it is the page's one way
to start anything.

**When.** After a decided move (the task crosses a full page load in the arrival note, as at most 12
content words, never the question); after the visitor picks an offered place for their question (tap or
"yes"); and at once when the visitor is already on the screen. That last includes the router's *likely*
place being the current page: then "Open Announcements?" to someone on Announcements is replaced by acting
there. A single-page app draws after it moves, so the page is looked at again at 250, 500, 900 and 1,500 ms
before giving up quietly. The panel docks so what opened can be seen, and a screen reader hears *"Opened
«New event»."*. A tab pressed on the way in is followed by one more look for the control inside it.

**The adopter decides how far.** `act: 'open'` (default), `'point'` (never press), `'off'`.

## Alternatives considered

**Do nothing: end at the page.** It is honest and safe, but it leaves the newcomer at the exact step they
fail at. The owner asked for more.

**Only point, never press.** It is the safest form, and it is `act: 'point'`. As the default it gives up
the case the owner described (the form open) for controls that say they open something, where pressing
has no side effect by construction.

**Press any control whose name starts a task.** It would work on the most apps, but it is the "New invoice
creates a draft" case: an act on the adopter's data, done by a guest, on a guess. Rejected. It is exactly
what "I don't change anything" rules out.

**Learn the app from its source only.** It is precise where it works. But it needs one reader per
framework and per UI library, and it silently gives nothing for everything else. Kept as the
*confidence* layer (`opens`) on top of the runtime reading, not as the mechanism.

**Record the adopter's clicks (a macro recorder).** It is exact, but it is a human step in the adopter's
app, which the product promises not to require, and every redesign breaks it silently. `knowledge.json`'s
`opens` is the cheap, reviewable version of the same knowledge.

**A model reads the page and decides.** It is the most general option. But it is a model call per
arrival, it cannot run offline (Rule 8), and a model choosing what to press is the unverifiable "safety
property that depends on a model call" ADR-009 rejects.

**Fill the form too.** Out of scope, by the owner's words ("doesn't fill in, yet"). Filling needs values
the visitor gave, a per-field mapping, and a far stronger rule on what may be written. It gets its own ADR
when it comes.

## Consequences

- **Its reach depends on the app's accessibility.** A control with no accessible name (an icon with no
  label) cannot be found. A dialog button that does not say it opens something is only pointed at, unless
  the source or `opens` says so. Accessible apps get more; others get the ring.
- **Word matching is narrow.** It uses the visitor's words, the destination's name and a light stem. There
  is no synonym list: "schedule a match" does not meet "New game". A mismatch between the language the
  visitor writes and the app's labels meets only near-cognates. The measured English run above failed for
  this reason.
- **Start verbs and never-verbs are closed lists in two languages.** A third language gets no tasks, and
  a label outside the lists ("Compose", "Draft") may be missed, or, for never-verbs, pressed when it
  should not be. The never-list is deliberately broad ("close", "leave", "sign" all block), so some
  harmless controls are never helped with.
- **`aria-haspopup` is trusted.** A control that declares a popup and also acts on press would be pressed.
  It would be an app bug, but the press is ours.
- **The source readers recognise a few idioms per framework.** They cover state setters, flags, toggles,
  `open…()` calls and `…Trigger` components. The markup reader works on text, not a parser, so an unusual
  template layout can hide a handler. A handler that shows something *and* does something else
  (`showForm = true; track()`) is not an opener. That is deliberate, and it means some real openers are
  missed.
- **Opener labels change a screen's examples, and so its vectors.** An adopter's calibration is only as
  current as their last `calibrate`, which `doctor` already reports. The measured run changed no golden
  decision, but it was one screen of one fixture.
- **The panel docks after pressing or pointing.** A visitor mid-conversation has to reopen it. The thread
  is kept.
- **2.1 KB of the widget budget.** 1.8 KB is left under 60 KB. The next feature of this size needs the
  budget revisited, or something removed.
- **The arrival note now carries words from the question.** They are in `sessionStorage`, same origin,
  gone when the tab closes, and at most 12 words, but they are the visitor's words, stored.
