# ADR-005 — AI-first, not AI-only: conventional navigation is retained

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Architect, Frontend
- **Supersedes:** —

## Context

The blueprint states: *"No menu required"* and *"The user should never need to know
where a feature is located."*

As a description of the target experience for a typical interaction, this is right and
it is the whole point of the project. As a literal architecture constraint — build no
conventional navigation — it fails.

This ADR exists because the distinction is easy to lose during implementation, and
because "we'll add navigation later if we need it" produces a worse result than
designing for both from the start.

## Decision

**The assistant is the primary interface. A complete conventional navigation structure
exists underneath it, secondary in placement and visual weight, but covering 100% of
routes.**

Concretely:
- The app opens on the assistant surface, not on a menu
- A nav drawer or bottom bar exists and reaches every registered screen
- Requirement FR-NAV-04: every screen reachable by AI is reachable without it, verified
  by manual traversal of the full registry
- The home surface shows capability tiles — tappable, and doubling as discovery

## Rationale

Four independent reasons, each sufficient on its own:

**1. Accessibility.** A screen-reader user, a user who cannot use voice, a user in a
noisy or silent environment — all need a traversable structure. WCAG 2.2 has no
conversational exemption, and NFR-A11Y-01 commits us to AA conformance.

**2. Discoverability.** Users cannot ask for features they don't know exist. This is
the fundamental limit of conversational interfaces and it does not get better with a
better model. Something must advertise the capability space.

**3. Failure degradation.** A ~700 MB model may fail to download, fail to load, or time
out. Stages 1–2 keep working, but confidence-gated routing will produce more `Clarify`
outcomes. Without conventional navigation, a model problem becomes a dead app. With it,
it becomes a degraded one.

**4. Speed on habitual actions.** For a screen visited daily, a tap is faster than a
sentence. Forcing conversation onto routine navigation is a regression the user feels
every single day.

## Consequences

**Positive**

- Accessible and usable when the model is unavailable
- Discovery problem addressed at the surface where it occurs
- Gives an honest measurement baseline for the "80% reduction in manual navigation"
  metric — you cannot measure a reduction in something you removed

**Negative**

- More UI to build and maintain
- A risk of the conventional path becoming the default through habit, undermining the
  premise. Mitigated by measurement: the trace-derived "actions completed via AI"
  metric (target 90%) tells us if this is happening.
- Two navigation entry points must stay consistent — mitigated because both are
  generated from the same registry.

## What this does *not* mean

It does not mean building a conventional app with a chat bolted on. The assistant is
the default surface, gets the primary screen real estate, and is the fastest path to
anything non-habitual. Conventional navigation is the floor, not the ceiling.

## Measurement

If the AI-completion rate is below target, the answer is to improve the router — not
to hide the menu.
