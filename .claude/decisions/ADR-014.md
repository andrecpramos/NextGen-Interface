# ADR-014 — Rule 17 ships as one registry per role, generated from one annotated master

- **Status:** Accepted — 2026-09-11
- **Date:** 2026-09-10
- **Deciders:** Maintainers
- **Supersedes:** —
- **Amends:** —

## Context

Rule 17 was written on 2026-09-09, forced by role-gated routes in a real application:

> **A capability the current user cannot reach is not in the registry they receive.** Not
> filtered at render — **absent**, so an unreachable route is never offered and its
> existence is never revealed. This is a security property, not a UX filter.

The rule says what must be true. It does not say what the generator writes to disk, and
A hand-written ground truth left that open on purpose: it annotated `roles` on each
capability, while the product description spoke of *"one registry per role"*. Both encode
Rule 17 equally well; a single annotated list is far less repetitive to author and review
by hand.

The generator has to emit something, so the decision cannot stay open. The two candidate
shapes are genuinely different artefacts:

- **(a) One registry, each capability annotated with its roles.** One file, easy to
  review, easy to diff, and the runtime filters on load.
- **(b) One `RegistryFile` per role, containing only that role's capabilities.** Ten files
  for a ten-role app, each one a plain registry the existing engine already understands.

A real application measured for this had ten backend roles and 145 generated
capabilities, so this is not a hypothetical difference: one role reaches 20 of them,
another 25, and a third 74.

## Decision

**Both, with a boundary between them: (b) is what ships, (a) is what is reviewed.**

The generator emits:

| Artefact | Contains roles? | Who sees it |
|---|---|---|
| `registry.<ROLE>.json` | **No** | The browser, at run time. One per role. |
| `master.json` | Yes, per capability | The adopter's developers, in review and in diffs. |
| `SKIPPED.md` | — | The adopter's developers. |

Concretely, in `emit.ts`:

```ts
const reachable = master.filter((c) => c.roles.includes(role)).map(withoutRoles);
```

**The `roles` annotation is dropped on the way out**, not merely unused. Telling a
`TEACHER`'s browser that a screen it can reach is *also* reachable by `ADMIN` and `FINANCE`
is a far smaller leak than the capability itself, but it is a leak, and nothing at run
time needs it: **the registry a session receives *is* its entitlement.** There is no
second filtering step for a bug to live in.

`core-capability`'s `Capability` type is therefore left alone — no `roles` field. The
shipped artefact is exactly the `RegistryFile` the engine already reads, which means
role-scoping costs the runtime nothing and cannot drift from what the runtime enforces,
because there is nothing left for it to enforce.

## Why not (a) alone

Because option (a) makes Rule 17 a *runtime* property, and Rule 17 is a *delivery*
property. A single annotated registry shipped to the browser contains, in plain text, the
route, title, description and example utterances of every administrative screen in the
application. A guardian opening dev tools would learn the shape of a safeguarding and
audit surface they must not know exists. Whether the client-side filter works is then
irrelevant — the disclosure already happened when the file was served.

It also puts the security property in the one place we do not control. The adopter
integrates the runtime; if their bundler inlines the registry, or their CDN caches it, or
a future version of our own loader reads the file before filtering it, the rule quietly
stops holding. Filtering at build time cannot fail that way.

## Why not (b) alone

Because ten files with 74, 65, 54, 44, 25, 25, 20, 20, 17 and 11 overlapping entries are
unreviewable and undiffable. A developer asking "did this change give `PARENT` something
new?" would have to diff two generated files against two previous generated files. The
master answers it directly, and it is where the generator's own tests and the ground-truth
scorer both look.

The cost is duplication: that app's ten registries contain 301 capability entries
for 145 distinct capabilities. That is accepted. These are build artefacts, regenerated
on every deploy, and a role's registry is exactly what that role's browser must download
anyway — the duplication is across files that are never fetched together.

## The reversibility test

**Reversible.** Both artefacts come from one in-memory inventory, and `splitByRole` is
nine lines. Moving to (a) means shipping `master.json` and filtering on load; moving to a
third shape means changing one function. No hand-written file encodes the choice, because
every registry is generated. Nothing outside the generator would need to change to
regenerate everything a different way.

What is *not* cheaply reversible is the disclosure: a registry shipped with every role's
capabilities in it cannot be un-served. That asymmetry is the whole argument.

## Consequences

- **Rule 17 is now testable by diffing artefacts**, and it is tested that way rather than
  by inspecting the code that produces them —
  [`emit.test.ts`](../../packages/generator/src/emit.test.ts) asserts that no string of an
  admin-only capability appears anywhere in a guardian's registry, and
  `score-generated.mjs` re-checks all ten
  generated registries against the master on every scoring run.
- **An application with no roles gets one registry** for a single `PUBLIC` audience, so
  the code path is the same everywhere and Rule 17 still means something on a three-route
  marketing site.
- **The browser runtime must ship the right registry per session.** The bundle a session receives is
  selected by role at serve time; that is a new requirement on the browser runtime, and it
  is the natural place for it, because it is now a file choice rather than a filter.
- **The install already assumes this** — "the bundle served to a session contains
  only that role's capabilities; an ADMIN capability is absent from a GUARDIAN bundle, not
  hidden" — and can now be verified against files rather than behaviour.
- **Per-role calibration (Rule 14) becomes per-file**, and each role's corpus is a
  different size: the smallest role sees 11 capabilities and the largest 74. Thresholds
  are an artefact of the registry, so ten registries need ten calibrations. The kit's
  `calibrate` and `eval/frameworks/calibrate-registries.mjs` do exactly that, one sweep
  per registry.

## Compliance

- Rule 1 — `@nextgen/generator` is not a `core-*` package and imports no domain;
  `check-import-boundaries.mjs` is green.
- Rule 10 — every generated capability ships 4 examples, and every example is a golden
  entry.
- Rule 13 — every role registry carries the declared boundaries, so a refusal is never a
  privilege.
- Rule 15 — the adopter's source text reaches a prompt only as delimited data, and the
  model writes prose only; route, role, id and kind are decided before any prompt exists.
- Rule 16 — `writeOutput` refuses an output directory inside the application's source, and
  the whole fixture tree is fingerprinted before and after a run.
- Rule 17 — this ADR.
