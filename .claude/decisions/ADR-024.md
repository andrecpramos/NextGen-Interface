# ADR-024 — What a visitor attaches never leaves their device; the page may take it, and the look is glass, metal and light in CSS

- **Status:** Proposed — the owner asked for both in session, 2026-09-21; this text awaits acceptance
- **Date:** 2026-09-21
- **Deciders:** Andre, Architect
- **Relates to:** [ADR-022](./ADR-022.md) — the orb and the CSS rebuilds, no React in the script tag;
  [ADR-021](./ADR-021.md) — the script tag in `adapter/` is what an adopter receives; Rule 8 (the
  device is the source of truth) and Rule 15 (untrusted text is fenced); WP-48, the prompt-injection
  defence that must land before any write or destructive capability.

## Context

The owner asked for two things. **A signature look**: the frosted, lit-edged, metal-rimmed surfaces of
the `/alive` bench (glassmorphism, metalmorphism, "light" morphism), in place of flat panels. And **photo
and file upload** in the assistant's box, "more for mobile" — a visitor who holds the thing they need help
with (a certificate, a receipt, a screenshot of an error) should not be told, by a box that only takes
typing, that the assistant is not for them.

Upload is not the same kind of feature as the rest of this product. Everything else the widget does is
local: it routes in the browser, calls nothing, and its egress gate (`check-network-egress.mjs`) exists
to keep it that way. The pilot's data is medical. A file is also untrusted input in the strictest sense:
its name, its type and its bytes are whatever the visitor's device says. And the assistant has nothing to
*do* with one — it navigates and explains, it has no vision, and stage 3 (off by default) is a
same-origin text proxy whose prompt is fenced against exactly this kind of content.

## Decision

**1. An attachment never leaves the visitor's device.** It is not sent to the router, written into a
`TurnTrace`, put in a prompt, or fetched anywhere. `ask` hands the router the words and nothing else. It
is shown back to the visitor (a picture drawn on a canvas by the browser's own decoder, or the file's
icon), and offered to the page the assistant sits in as a cancelable `nextgen:attach` event carrying
`{ files, utterance, route }` — the same shape as `nextgen:navigate`, for the same reason: a strict
Content-Security-Policy leaves a script-tag page no other channel. The visitor is told which happened
("I've passed your attachment to the app" / "your attachment stays on this device — I can't read it"),
and a message that is only a file is answered, not refused, and asked the one question that lets the
assistant help: what to do with it.

**2. The limits are declared, and are a courtesy.** Four files, 15 MB each, photos and common documents;
SVG, HTML, scripts, archives and executables are turned away by name *and* by type (Rule 13). A file
input's `accept` is a hint and is not enforced on a paste or a drop, so every way in is judged by the same
function. A page that takes a file must check it itself: the widget's checks are not a security boundary.

**3. It is on by default, and an adopter can turn it off** (`data-nextgen-attach="off"`, or `attach:
false`). An app with nowhere to send a file should not offer a button that goes nowhere; the installing
agent is told to ask (ASK 5) and never to wire an upload endpoint on its own initiative.

**4. The look is CSS, derived from the host.** Glass is the host's own raised surface made translucent
with a lit top-left edge; the metal is the host's accent, lit above and shaded below in a bright rim; the
light is the host's accent, softly, behind the glass (an "aurora" on the opaque backdrop, without which
glass over a flat colour is only a grey rectangle). Every value is computed from the page's scheme and
accent in `theme.ts`, so it reads as part of *their* application, and a light host gets white glass with
soft depth. Blur is spent only where something is behind (composer, corner controls, drawer, docked
bubbles) — not on every message. Where the browser cannot blur, or the visitor asks for reduced
transparency, or forced colours are on, every surface is the host's solid colour, as before.

## Alternatives considered

- **Send attachments to a model (vision).** Rejected: it would be the first thing in the product to send a
  visitor's data anywhere, with medical data in the pilot, and it would put untrusted binary content next
  to a prompt whose defence (WP-48) has not been written. Reversible later behind an explicit adopter opt-in;
  not now.
- **Route by attachment** — find the app's screen that has an upload form and take the visitor there. The
  right next step, and not done: it needs the scanner to record which screens take a file (a schema change
  in `core-capability`) and a golden set to keep it honest. Recorded in STATUS.
- **`blob:` URLs for previews.** Rejected: they are what a strict CSP refuses for `img-src`. A canvas is not.
- **WebGL metal (`metal-fx`) for the primary button.** Rejected in ADR-022 for the same reasons: React,
  WebGL2, and a machine-stalling shader. The metal here is a gradient and a rim.

## Consequences

- A visitor can attach a photo (camera or library, on a phone), paste one, or drop a file, and is always told
  what became of it. Without the adopter's wiring it is honest but inert; that is the price of "nothing
  leaves the device", and it is what the owner should judge on a real app.
- The script tag grows (about +12 KB gzipped across today's glass and attachments; 50.5 KB in total).
- `nextgen:attach` is a public event: the adopter's page receives `File` objects and must validate them.
  Documented in `doctor`, `AGENTS.md`, and the embed README.
- Not measured: the look on a low-end phone (blur cost), a HEIC photo outside Safari (falls back to the
  icon), and a real `as-needed` locale app (STATUS).
