# ADR-023 — The adopter tells the assistant about their app: `knowledge.json`, written in an interview

- **Status:** Accepted — 2026-09-22. Proposed 2026-09-21 ("the assistant is too dumb, very low
  knowledge of the webapp… the agent asks the adopter open questions"). Accepted on fixture
  evidence; an acceptance run on a real application remains the test that counts (Consequences)
- **Date:** 2026-09-21
- **Deciders:** Maintainers
- **Relates to:** [ADR-019](./ADR-019.md) — the model may write, claims validated; [ADR-021](./ADR-021.md)
  — the copied folder's scanner cannot use a model; [ADR-017](./ADR-017.md) — stage 3;
  Rules 10, 13, 14, 15.

## Context

The complaint is the one made on 2026-09-18 (ADR-019), made again after using the product: the assistant reads as a menu, knows almost nothing about the app it serves, and does not
reason.

Measured on 2026-09-21, through the real router with the reference fixture's registries and no
model, on 14 ordinary questions a parent might ask (Portuguese, written before any change):

- **2 reached a screen.** Both were near-literal title matches ("estado médico", "painel"). Ten
  got a menu of five options back. "How much do I owe this month" was refused for the wrong reason.
- On the 10 in-scope ones, the right screen was **ranked first in 6**, executed in 2, and a wrong
  screen executed in 0. On the golden set (now 69 turns, 55 in-scope), 25.5% of in-scope turns executed the right screen.

Three causes, all in the code as it stands:

1. **A screen is a title and a template sentence.** `Anúncios is a screen in the communication area
   of this application, at /my/announcements.` Nothing says what it is *for* or what is on it.
2. **The offline matcher is lexical.** Stage 2 is TF-IDF over a vocabulary built only from the
   registry's own text (`embedder.ts`): a word that appears in no screen's record contributes
   nothing, so "magoou-se" can never find a screen that never says it.
3. **Nothing asks the person who knows.** All eight `ASK`s in `adapter/AGENTS.md` are install
   logistics. None is about the app.

The scanner cannot write better prose: it has no model, by construction (ADR-021), and the two
fixes the tool already had — a model at build time, or a model at run time (stage 3) — cost the
adopter a server and send visitors' text off the page. The person who has the knowledge is the
adopter, and the thing they can be asked for, once, at setup, is data.

## Decision

**We will give the adopter a file to say what the scanner cannot, make the installing agent
interview them for it, and merge it into the registry deterministically and offline.**

1. **`knowledge.json`**, beside `nextgen.config.json` (or where the config's `knowledge` points),
   owned and committed by the adopter. Four sections: `app` (what it is for), `glossary` (their
   terms and the everyday words for them), `screens` (per route: `purpose`, `contains`,
   `aliases`, `askedAs`) and `cannot` (limits: `about`, `say`, `askedAs`).
2. **It is merged into fields already indexed and served** — `description`, `examples`,
   `explanation`, plus new declared limits (Rule 13) — so the matcher, `capabilityDocument` and
   the widget are untouched. `purpose` is served verbatim as the explanation; the app summary
   becomes the domain description stage 3 is given.
3. **It is untrusted input** (Rule 15): parsed never cast, text cleaned and capped, prototype-
   polluting keys refused, and a file it cannot fully read is a *warning naming the path*, never a
   crash and never a silent drop. A path outside the config's folder is not read.
4. **`build` writes `review/KNOWLEDGE-GAPS.md`** — what the tool does not know, as questions, screen
   by screen — and `doctor` reports coverage. This is the interview's script.
5. **`adapter/AGENTS.md` gains ASK 9, the interview**, run after the first `build` and before
   calibration, in **open questions** the developer answers in their own words, and **ASK 10**, which
   hands the conversation back so the developer can ask theirs. The agent must not invent an
   answer, must not reuse `askedAs` phrasing in the calibration set, and must say "I don't know"
   rather than guess.

## Measured

Reference fixture, knowledge written by the author of the tool (a model, standing in for a
developer), with the derived examples kept and the thresholds re-swept (Rule 14):

| | before | after |
|---|---|---|
| Golden set, 55 in-scope turns: executed the right screen | 25.5% | **61.8%** |
| … right screen ranked first / in top 3 | 72.7% / 87.3% | **87.3% / 100%** |
| Golden set, 14 out-of-scope turns: refused | 50.0% | **71.4%** |
| … wrong screen executed / in-scope wrongly refused | 0 / 2 of 54 | 0 / 0 of 55 |
| 10 everyday questions: right screen ranked first | 6 | **9** |
| … likely screen offered first, and right | 2, right in 1 | 3, right in 3 |
| … out-of-scope refused (of 3) / in-scope wrongly refused | 2 / 0 | 3 / 0 |

Declaring the app's own limits (`cannot`) cost about one right execution on the golden set and
bought back the out-of-scope refusals that the vocabulary change alone had lost (1 of 3).

**And it caused a false refusal, found only by a screenshot.** A "payments" limit whose phrases
included *mensalidade* refused "*tenho alguma mensagem nova?*" — an ordinary question about a screen
the app has — because the offline matcher works on fragments of words and *mensagem* and
*mensalidade* share "mens". The golden set said 0 of 54 wrongly refused, and was right, because no
golden question exercised the collision. It is now golden entry `sch-0069` (Rule 12), which shows
1 of 55 with the old phrase and 0 of 55 with the new one, and the interview (ASK 9) has the agent
test each limit against ordinary questions that share its words. The structural cause is not
fixed: a declared limit wins whenever it beats the best screen at all (`boundaryMargin` is 0),
which is calibrated on a golden set that had no counter-example. A floor for declared limits
is the next thing to calibrate, and needs more such entries to calibrate against.

## Alternatives considered

**Do nothing.** The assistant stays a menu. Rejected: it is the stated defect, twice.

**Let the scanner write descriptions with a model.** ADR-018/021 removed this on purpose: the
copied folder carries no model client and makes no network call. It would also put unreviewed model
prose in front of visitors as the app's own voice.

**Turn stage 3 (a run-time model) on by default.** It reasons, but every adopter must run and pay
for an endpoint and send visitor text to it, and a plain script-tag install stops working alone.
The product owner chose knowledge first, model as an upgrade. Stage 3 is unchanged and remains ASK 8.

**A semantic embedder in the browser.** A real sentence encoder is tens of megabytes against a 40KB
script tag, and ADR-017 measured the model path at about 800MB. It would still not know the app's
own words.

**Let the agent write the file from reading the source.** Fast, and what an agent will do if not
told otherwise. Rejected as the source of `purpose` and `cannot`: those are served to visitors as
fact, and the developer is the only one who knows whether they are true. An agent may *draft*; the
developer confirms every word.

## The reversibility test

**Cheap to reverse in code, expensive in the file.** Removing the merge is a deletion in
`generate()`; `knowledge` is an optional argument and an absent file changes nothing. But once an
adopter has written a `knowledge.json` the schema is a compatibility surface: renaming a key means a
migration in their repository. So the four sections are small, unknown sections are reported
rather than rejected, and a schema version field is the first thing to add if it must change.

## Consequences

- **The evidence is thinner than the numbers look.** The knowledge was written by a model, on a
  small synthetic fixture, and the golden set is easy — it was written from the app's own labels.
  FIELD-NOTES §4 found on a real app that model-written examples routed *worse* than derived ones.
  These are additive to the derived ones, which is why they help here, but **an acceptance run on
  a real application, with a real developer answering, is the test that counts.**
- **The phrasing rules are learned, not proven.** Requests, the users' main language, only what the
  screen does, five or more — from that field note. Nothing enforces them yet.
- **Knowledge can attract the wrong intent.** Writing "share with the coach" into the medical
  screen made "talk to the coach" rank it first (it is still not executed: the thresholds hold). The
  fix is a declared limit, which is why `cannot` is in the file.
- **Offline, the assistant recognises more but still does not reason.** It says what a screen is for
  in the adopter's words. Judgement across screens is stage 3 (ASK 8), and stage 3 now reads this
  file too — see the addendum below — but **whether that makes a live model answer better has not
  been measured**: no model server was available, and `router:eval` needs one. What is proven is
  the plumbing and the safety, not the improvement.
- **It asks the developer for time.** An interview and a file to keep current. The alternative to
  their time is the current assistant.
- **`purpose` is now the app speaking in the adopter's voice.** A wrong one is served as fact until
  someone edits a string, which is the point of serving it verbatim, but it is a new way to
  be wrong.

## Addendum, 2026-09-21 — the model stage reads the file too

The product owner asked that the model stage be given as much of the app's knowledge, and of the reasoning
the app requires, as possible. Two additions, both to the same file and the same rule that nothing
is trusted at run time that was not validated at build time.

1. **`rules`** — short statements about how the app works: what depends on what, what must be known
   first, where people go wrong ("medical status is per child"; "messages almost always means
   announcements, not notifications"). They are the reasoning a newcomer would not guess, written
   down. Each rule, and each glossary entry, may name `roles`.
2. **`RegistryFile.context`** — `{ glossary, rules, limits }`, an optional block on a role's registry.
   The generator writes into each role's registry **only what is for that role**, so a rule scoped to
   ADMIN is absent from a guardian's file altogether (Rule 17: the registry is the entitlement; it is
   not filtered when read). Unscoped rules go to every role, which the interview says out loud.
   `validateRegistry` refuses a malformed or oversized one. `core-capability` and `core-intent` gain a
   generic field and read it the way they read `domainDescription`: no subject matter enters an
   engine (Rule 1), and a second application changes nothing in `core-*`.
3. **Stage 3** puts it in a `<knowledge>` region of the prompt, every string through `redactTag` (Rule
   15), inside a 4,000-character budget with rules first. The system message says only what the tags
   mean, and asks for reasoning from the rules when there are rules. **A registry without any produces
   the prompt it always did, byte for byte**, so nothing calibrated moves; that is a test.

What this does not do: change anything a visitor sees when stage 3 is off, which is the default
(ASK 8). And it adds a way to be wrong: a rule is served to the model as fact about the app, so a
wrong one steers it. The interview forbids inventing them, as with `purpose`.

Not measured, and worth saying twice: the reference app's rules were written by the tool's author, and
no live model has read them. The next step that would tell us whether this helps is `router:eval` on
a model server with and without `context`.

## Compliance

- **Enforced by tests:** `knowledge.test.ts`, `knowledge-file.test.ts` (parsing hostile files,
  the merge, determinism, gaps, limits), `kit.test.ts` (it reaches the served registry, leaves the
  app byte-for-byte unchanged, warns with the path), `agents-md.test.ts` (the interview keeps its
  safeguards), and the existing derived-artefacts and golden-set gates over the regenerated fixture.
- **By convention only:** that the interview is actually run, that the agent does not invent
  answers, and that `askedAs` is not reused in calibration. Nothing can check that a conversation
  happened; `doctor` reports coverage, which is the nearest signal. This belongs in
  `critical-infrastructure.md`'s gap list.
