# ADR-021 — The tarball path is retired; `adapter/` is the only way in

- **Status:** Proposed — the decision was made by the owner in session, 2026-09-20; this
  text awaits acceptance
- **Date:** 2026-09-20
- **Deciders:** Andre, Architect
- **Extends:** [ADR-018](./ADR-018.md) — it chose the folder as the unit of distribution
  and kept the tarballs "until `adapter/` is finished". This ends that transition.
- **Relates to:** [ADR-017](./ADR-017.md) — the model path the copied folder deliberately
  does not carry; Rules 1 and 16.

## Context

ADR-018 made the unit of distribution a folder an adopter copies, and left the eight-then-six
tarballs in place as a bridge: *"Until `adapter/` is finished, the tarballs are still how
this installs."* By 2026-09-20 `adapter/` is finished in the only sense the repository can
check. `build-adapter.mjs --check` proves the committed folder is what `packages/` builds,
and `check-adapter.mjs` copies it into a directory with no `node_modules` above it and runs
`init`, `build` and `doctor` for real. All four M6 work packages (WP-52 to WP-55) shipped
through it.

The bridge was never taken down, so the repository carries two install paths for one
product, and they contradict each other in what an adopter is told to do:

| | Tarball path | Folder path |
|---|---|---|
| Adopter is told | `gh release download`, `npm install -D vendor/nextgen/*.tgz`, `npx nextgen …` | `node <here>/scan.mjs …` |
| Written in | `GETTING-STARTED.md`, `INSTALL.md`, `CHANGELOG.md` | `adapter/AGENTS.md` |
| Needs | private release access, npm, a `node_modules` | nothing |
| Can reach a model server | yes — `cli.ts` passes `ollamaModel` | no, by construction |

Measured on 2026-09-20, the tarball path is:

- 1 workflow (`release.yml`, 92 lines) and 4 scripts (`pack-release`, `check-install`,
  `check-packaging`, `check-release`: **734 lines**), three of which run on every pull
  request;
- 6 byte-identical `LICENSE` copies, 6 `tsconfig.build.json`, and `files` / `publishConfig`
  in 6 manifests, all present only so `pnpm pack` produces something installable;
- `packages/kit/src/cli.ts` beside `cli-copied.ts`, and the `bin` field pointing at it;
- `INSTALL.md` (329 lines) and `CHANGELOG.md` (76 lines).

It also makes the product explain its own duplicate. `adapter/AGENTS.md` has a paragraph
telling the installing agent that if it has seen a `--model` flag documented, *"that is the
npm-installed version; this is the copied one, and they differ deliberately."*

**Nothing was ever released.** There is no `v*` tag locally or on the remote, and
`CHANGELOG.md`'s only section is headed *"0.1.0 — unreleased"*. No adopter has installed by
tarball, so removing the path breaks no one.

Separately, ADR-018 recorded that Rule 1 *"loses its subject"* once the domain packages were
deleted, and that `check-import-boundaries.mjs` *"must be repointed or retired"*.
`critical-infrastructure.md` §2 then recorded that it *"cannot currently fail for the reason
it exists"*. Three days on it still reports *"3 core package(s) clean of domain imports"*
against a tree with no domains.

## Decision

**We will make `adapter/` the only way an adopter installs this, and delete the tarball path.**

Removed:

- `.github/workflows/release.yml`; `tooling/scripts/{pack-release,check-install,check-packaging,check-release}.mjs`,
  and the `pack:release` script;
- the `LICENSE` copy and `tsconfig.build.json` in every package, and `files`,
  `publishConfig` and `bin` from every manifest;
- `packages/kit/src/cli.ts`. `cli-copied.ts` is the only entry point, so the `Capabilities`
  seam in `run.ts` and the `model` / `endpoint` / `proseModel` options in `build.ts` — which
  only `cli.ts` ever filled, and no test exercised — go with it. `--model` becomes an explicit
  refusal (exit 2, with the reason) rather than a flag that is silently ignored;
- `packages/kit/src/agent-playbook.ts` and the `nextgen/AGENT.md` that `init` wrote from it.
  It was a second copy of `adapter/AGENTS.md` for the npm path, and it had drifted in the way
  such copies do: its ASK 7 offered `--model <name>`, which the copied tool refuses. `init`
  now points at the `AGENTS.md` beside the tool, and `doctor` does the same;
- `INSTALL.md` and `CHANGELOG.md`. The one part of `INSTALL.md` that was not about the
  tarball path — the owner's acceptance run (WP-35) — is kept, rewritten for the folder path,
  as `.MDFiles/ACCEPTANCE-RUN.md`.

Changed:

- **Every package is `private: true`.** They are workspace source that builds `adapter/`;
  saying so in the manifest is the honest signal that none is installable.
- **`pnpm build` builds the widget** (`packages/embed/dist/nextgen.js`) and nothing else,
  because that is the only build output anything consumes. `tsc` declaration output existed
  only for the tarballs.
- **`GETTING-STARTED.md` describes the folder path**, and agrees with `adapter/AGENTS.md`.
  The tool's own messages said `Run "nextgen build"` in about fifteen places, naming a command
  that is not on an adopter's PATH; they now say `node scan.mjs build`.
- **`packages/embed/build.mjs` writes the script tag only.** The ES-module bundle beside it
  existed for `import { start } from '@nextgen/embed'`, and nothing read it.
- **A release is `main` moving**, when the owner asks for it. An adopter copies `adapter/`
  from the commit they choose. There is no version number and no release notes file;
  ADRs and git history are the record.

**We will also repoint Rule 1** from the vacuous *"core never imports a domain"* to the
invariant that survives the deletion and that a gate can still fail on: **`packages/core-*`
depend only on other `core-*` packages** — never on `generator`, `embed` or `kit`, in
`package.json` or in an import specifier. The engine sitting below everything that reads or
serves an application is what keeps it from learning about one. The gate is repointed, not
retired, so no enforced rule is dropped.

## Alternatives considered

**Do nothing — leave both paths.** Costs nothing today, and it is the state the repository
has been in since 2026-09-17. Rejected because the cost is not today's: every gate on the
tarball path runs on every PR (`check-install` alone is 360 lines and fetches Node 20 over
the network), every future agent must work out which install instructions are live, and the
duplicate keeps generating contradictory documentation. This was the option we had, and it
is why the mess was still there to be found.

**Stop advertising the tarball path but keep the machinery.** Removes the confusion and none
of the code. Rejected because the machinery is what an agent will keep maintaining: a path
that is *"deprecated"* but gated in CI is a path someone keeps green. If it is not going to
ship, it should not be kept passing.

**Ship `adapter/` as a release asset (a zip on a GitHub Release).** It keeps a version
number and a checksum, which the folder path lacks. Rejected for now because it
reintroduces exactly what ADR-018 removed: a private release as a prerequisite to trying the
product. If adopters turn out to need a version identity, that is an additive change to
`build-adapter.mjs` and does not need the tarballs back.

**Publish the packages to a registry.** Rejected: the licence is proprietary and needs a
written agreement, and a public registry would publish the source.

## The reversibility test

**Cheap to reverse, because nothing shipped.** Every deleted file is one `git revert` away,
and no adopter depends on any of it. This is the cheapest moment to make this decision: a
tarball path with a first adopter on it would need a migration and a deprecation period.

The part that is expensive to reverse is unchanged from ADR-018 and is not made worse here:
once an adopter copies `adapter/`, its layout and `AGENTS.md` are what their agent was told
to expect.

## Consequences

- **The widget can no longer be imported as an ES module** (`import { start } from
  '@nextgen/embed'`), and no TypeScript declarations ship. An adopter uses the script tag;
  a single-page app keeps navigation in its router with the `nextgen:navigate` event, which
  `GETTING-STARTED.md` already describes. A team that wants a typed, bundled import has no
  path to one.
- **`nextgen build --model` is unreachable from the kit.** The Ollama-backed prose model for
  descriptions came only through `cli.ts`. The generator's own CLI
  (`pnpm --filter @nextgen/generator generate --model …`) still has it, so the capability
  survives for work in this repository and is absent from what an adopter receives — which
  is what ADR-018 D-6 already wanted for the copied folder.
- **`adapter/` carries no version.** An adopter cannot say which release they have, only
  which commit they copied from, and an upgrade is *replace the folder, run `build` again*.
  This is a real regression against tarballs with a `SHA256SUMS.txt`, accepted because
  there is no adopter yet to regress for. It is the first thing to revisit if one appears.
- **`npm ci` reproducibility through vendored tarballs goes away.** The replacement is the
  one `AGENTS.md` ASK 1 already proposes: commit the tool folder, so a build elsewhere is
  reproducible from the repository alone.
- **Three claims lose their gate**: that the packages install on Node 20 through npm, that
  every entry point resolves once published, and that the versions agree. None describes
  anything an adopter receives any more. The Node 20 claim is still tested where it now
  matters: `check-adapter.mjs` runs the copied folder, and `build-adapter.mjs` targets
  `node20`.
- **`CHANGELOG.md` is deleted with the numbers in it.** Its measured section quoted the
  private pilot's 69.9% / 53.4% figures, which the README already withdrew as unverifiable.
  What generalises is in `adapter/FIELD-NOTES.md`.
- Rule 1's restated wording is **narrower in what it names** and **broader in what it
  checks**: it no longer says "domain", and it now also refuses `core-*` depending on
  `generator`, `embed` or `kit`, which the old gate could not see.

## Compliance

- `node tooling/scripts/build-adapter.mjs --check` — what is committed in `adapter/` is what
  `packages/` builds. Unchanged, and now the only artefact-staleness gate needed.
- `node tooling/scripts/check-adapter.mjs` — a copy of `adapter/` runs with nothing installed
  and no network. **Extended by this ADR** with four checks that hold what it changed *where it
  runs*, in a bare directory: `init` writes no second `AGENT.md`; `doctor` names an
  `AGENTS.md` that exists beside the tool; no message from `init`, `build` or `doctor` tells the
  adopter to run `nextgen <command>`; and `build --model` is refused with a reason. The
  wrong-command pattern was shown to catch the old wording, so it is not vacuous.
- `node tooling/scripts/check-import-boundaries.mjs` — **repointed** to the restated Rule 1.
  Proven live by adding an import from `core-intent` to `@nextgen/generator` and confirming
  the gate exits 1 naming the file and line, then removing it.
- **Convention, and therefore a row in `critical-infrastructure.md`:** no package is made
  installable again without an ADR superseding this one.
