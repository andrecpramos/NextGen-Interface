# ADR-019 — The assistant may write to the visitor, and every claim it makes about the app is validated before they see it

- **Status:** Accepted — 2026-09-18
- **Date:** 2026-09-18
- **Deciders:** Maintainers
- **Depends on:** [ADR-017](./ADR-017.md) (accepted the same day) — there is no model to
  write anything without its transport.
- **Amends:** the reading of Rule 9 that produced ADR-017 point 4.

## Context

The product owner's requirement, stated 2026-09-18:

> *"O nosso interface deve adotar conhecimentos da app, e também alguma inteligência para
> conseguir manter uma conversa com os futuros usuários … para os usuários sentirem 'isto
> é útil' e não 'isto é chato'."*

Everything a visitor reads today was written at build time. The model's entire output is
one declared id chosen from a shortlist. That is why the assistant reads as a menu: asked
something it cannot settle, it can only offer choices or ask back. Measured, stages 1 and 2
settle **15.7%** of turns; the other 84% get a question in return.

Rule 9 — *"Every turn produces a TurnTrace. Explainability is a record, never model
narration"* — has been read as *the visitor never sees model text*, and ADR-017 wrote that
down. Read precisely, Rule 9 is about **explainability**: the answer to *"why did it send
me there"* must come from the recorded trace rather than from a model describing its own
reasoning. It does not, by itself, forbid the model from phrasing an answer.

Rule 2 already draws the line the other way round, and in the model's favour:

> The model **never computes a number the user sees. It phrases; code computes.**

So phrasing was always sanctioned. What was never settled is how far the phrasing may go.

**The product owner was offered three positions and chose the widest:** free text, with the
registry as context — over "phrase only declared facts", and over keeping the status quo.

## Decision

**The model writes freely. Before a visitor sees it, every claim it makes about the
application is checked against the registry that visitor received, and an unsupported
claim is removed rather than shown.**

Three parts, and the third is the one that makes the first affordable.

### 1 · It writes

Stage 3 gains a second job. It already selects a capability id; it may now also return
prose, and the assistant renders it. The prompt carries what the role's registry declares —
screen titles, descriptions, explanations, guided steps, declared limits — as context, not
as a template to fill.

### 2 · It is told what it does not know

The system prompt states plainly what the assistant cannot do: it navigates and explains,
it performs no actions, it has no access to the visitor's data, and it must not invent a
screen. Prompt instructions are guidance, not enforcement — which is why part 3 exists.

### 3 · Every claim about the app is validated before display

This is **Rule 4 applied to prose**. Rule 4 already says *"every model-produced identifier
is validated against the registry before use"*; until now the only identifier was the
chosen id. Free text produces identifiers too — screen names, routes, field labels — and
they get the same treatment:

| What the model wrote | What happens |
|---|---|
| A route or screen name that is in this role's registry | kept, and rendered as a real link |
| A route or screen name that is **not** | the sentence naming it is dropped, and the turn degrades to the offer it would have made anyway |
| A claim to have done, saved, sent or changed anything | dropped. The widget has no dispatcher; it cannot have done it |
| A number the visitor would act on | dropped (Rule 2, unchanged) |

**The validator's output is part of the trace.** What was written, what was removed and
why is recorded, so *"why did it say that"* is still answered from a record — which is
Rule 9 satisfied rather than waived.

**A turn whose prose is entirely removed degrades to today's behaviour**, which is a
correct answer rather than an error: the offer of up to three screens, or a clarifying
question. The floor does not move.

## Why not the alternatives

**Phrase only declared facts.** Recommended, and rejected by the product owner. It is safer and it
reproduces the menu problem in better English: a visitor asking *"can I change my child's
medical status myself?"* needs an answer synthesised from a screen's purpose and a declared
limit, not either sentence quoted back. The cost of the wider choice is carried by part 3.

**Keep the model silent.** The status quo, and the thing the product owner asked to change.

**Trust the prompt.** The cheapest version of this decision: tell the model not to invent
screens and ship it. This project has already measured what that is worth — `llama3.1:8b`
obeys an instruction placed inside a fence, and `gemma3:1b` never once chose
`out_of_scope` across 140 calls despite being asked to. **A prompt is a request; the
validator is the guarantee.**

## The reversibility test

**Cheap to reverse, and cheap to narrow.** The validator sits between the model and the
surface, so tightening it — from "drop unsupported sentences" to "drop all prose" — is a
configuration change that returns the product to today's behaviour exactly. Widening later
is also possible. What would be expensive is shipping prose to real visitors with no
validator and then adding one, because by then the thing being removed is something people
have relied on.

## Consequences

- **Rule 9 is restated, not weakened** ([docs/RULES.md](../../docs/RULES.md)): explainability remains a record, and
  the record now includes what the model wrote and what was removed.
- **Rule 4 is widened**: identifier validation covers prose, not only the selected id.
- **Rule 15 matters more.** More of the adopter's text reaches a prompt, and that text is
  untrusted. Fencing is unchanged and the gate still runs; the volume going through it
  grows.
- **An adopter with stage 3 off sees none of this.** Prose requires a model; a model
  requires ADR-017's opt-in. The default build is unchanged.
- **The assistant can now be wrong in a new way** — fluent and unhelpful rather than
  fluent and false. The validator catches claims about the application; it cannot catch a
  sentence that is true and useless. That is a quality problem, measured by the golden set
  and by people, not a safety one.

## Compliance

- `validateClaims` in the render path, with the removal recorded in the `TurnTrace`.
- A golden-set bucket whose entries assert that prose naming an absent screen is removed.
- An adversarial bucket: prompts that try to make the model claim it performed an action.
- `check-prompt-fencing.mjs` — unchanged, and now covering a larger prompt.
