# ADR-004 — Action policy: capability kinds, confirmation, and undo

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Architect, Backend, Security
- **Supersedes:** —

## Context

The AI can execute actions against financial data. The router is statistically
accurate, not certainly accurate — stage 3 will sometimes be confidently wrong, and
speech recognition will sometimes hear "twenty" as "twelve".

The question is not whether misinterpretation happens. It is what the system does when
it does.

An additional pressure: transaction memos and imported files are attacker-controllable
text that may enter prompts. Prompt-level defences are advisory. Enforcement has to be
somewhere the model cannot reach.

## Decision

**Every capability declares a `kind`, and the dispatcher — not the prompt, not the
model — enforces policy on it.**

| kind | Policy |
|---|---|
| `read` | Execute immediately. No confirmation. |
| `write` | Confirmation card showing **parsed parameters**, editable in place, before execution. |
| `destructive` | Confirmation + an undo token recorded in the journal + trace entry. |
| *unclassified* | **Refuse.** Fail closed. |

Supporting rules:

1. **The confirmation card shows the parsed interpretation, not the utterance.** A
   misheard amount or a wrong category is visible as a field, and correctable in place
   without restating the sentence.
2. **Undo survives navigation.** A destructive action's undo affordance persists beyond
   the screen it happened on.
3. **No capability performs an irreversible external effect.** No payments, no
   transfers, no sending. Adding one requires a new ADR and a security re-review.
4. **Confirmation is not skippable by configuration.** There is no "don't ask me
   again" for `destructive`.

## Rationale

**Enforcement must live in code, not in the prompt.** A prompt instruction saying
"always confirm before deleting" is a suggestion to a probabilistic system, and it is
bypassable by injected text. The dispatcher is neither.

**Fail-closed on unclassified is the important half.** The realistic failure mode is
not someone deliberately marking a delete as `read` — it is someone adding a capability
and forgetting to classify it. Defaulting to `read` would silently grant free execution
to whatever comes next. Refusing produces a loud, immediate, harmless failure at
development time.

**Confirmation is where speech errors get caught.** STT will mishear amounts. Showing
the parsed number as an editable field converts an invisible data-corruption bug into a
visible, one-tap correction.

**Read/write asymmetry keeps the experience fast.** The large majority of turns are
questions. Confirming those would make the app tedious and train users to tap Confirm
reflexively — which destroys the value of confirmation exactly where it matters.

## Consequences

**Positive**

- A misrouted write cannot silently corrupt financial data
- Injection cannot reach a destructive action, even if it reaches the prompt
- The confirmation-rejection rate becomes a production quality metric — the earliest
  available signal that the router is degrading in the field
  (deployment.md)

**Negative**

- An extra tap on every write. Accepted deliberately.
- Undo requires a journal, which adds schema and complexity to every destructive path.
- Confirmation-card UI has to be built per capability shape, not once generically —
  though the param specs make most of it generatable.

## Enforcement

- The unclassified→refuse path has a dedicated test
- The adversarial golden-set bucket asserts **zero** destructive outcomes
- Security review is required for any PR adding a `write` or `destructive` capability
  ([security.md](../docs/security.md))
