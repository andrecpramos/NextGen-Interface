# ADR-001 — Flutter + Riverpod + GoRouter as the client stack

- **Status:** ⚠️ **SUPERSEDED by [ADR-006](./ADR-006.md)** — the stack is TypeScript, not Flutter
- **Date:** 2026-08-29
- **Deciders:** Architect
- **Supersedes:** —

> **Read ADR-006 instead.** This decision was made before evidence about the
> developer's actual working stack existed. Kept for the record: its analysis of
> *why* FFI access is the binding constraint for on-device inference remains
> accurate, and ADR-006 accepts that Flutter was genuinely the stronger option on
> that one axis.

## Context

We need one codebase across Android, iOS, and eventually web and desktop, with a
navigation system an AI layer can drive programmatically, and FFI access to C/C++
inference libraries (llama.cpp, whisper.cpp, Piper).

The FFI requirement is the binding one. On-device inference means calling native
libraries; a stack without first-class FFI is disqualified regardless of its other
merits.

## Options considered

| Option | Verdict |
|---|---|
| **Flutter** | Mature `dart:ffi`, single codebase incl. desktop, GoRouter is declarative and drivable |
| React Native | Viable; FFI via JSI/TurboModules is workable but more per-platform native code |
| Native ×2 | Best per-platform inference story, ~2× the work — untenable solo |
| KMP + Compose Multiplatform | Excellent native interop; iOS UI story less mature; smaller Flutter-comparable ecosystem for our needs |

## Decision

Flutter, with **Riverpod** for state and **GoRouter** for routing.

Riverpod: compile-safe DI, testability without a widget tree, and the ability to
compose providers across layers without a service locator. It matters here because the
composition root must wire domain interfaces to infrastructure implementations, and
tests must swap in a fake LLM runtime trivially.

GoRouter: declarative, URL-based, and — critically — routes can be constructed
programmatically from generated code. The AI produces a route string and params; the
`NavigationEngine` validates against the registry and executes. That indirection is
only clean if routing is declarative.

## Consequences

**Positive**

- One codebase; `dart:ffi` gives direct access to llama.cpp/whisper.cpp/Piper
- Registry-generated routes can feed GoRouter and the intent engine from one source,
  so they cannot drift
- Riverpod's overrides make fake-runtime integration testing straightforward

**Negative**

- **Web does not get on-device llama.cpp.** The single-codebase promise does not extend
  to inference. Web needs WASM/WebGPU or a cloud fallback — decide explicitly, do not
  drift into it ([deployment.md](../docs/deployment.md)).
- FFI binding work is real and platform-specific: build flags, ABI variants, isolate
  management to keep inference off the UI thread.
- Flutter app size baseline plus native libs eats into an already tight budget before
  models are considered.

**Neutral**

- Dart's ecosystem for ML tooling is thin. Acceptable — we consume C libraries via FFI
  rather than doing ML in Dart.

## Current blocker

The Flutter SDK is **not installed** on the development machine (verified 2026-08-29:
`flutter` and `dart` absent from PATH and all common install locations). Sprint 0.1
covers this. Router work does not depend on it — see [ADR-003](./ADR-003.md).
